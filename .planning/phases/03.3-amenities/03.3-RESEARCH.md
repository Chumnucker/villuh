## Summary

Amenities is **greenfield code inside a pattern set that has already shipped the exact building blocks 3–4 times.** There is essentially nothing to invent: the catalog↔assignment↔denormalization model is `organization_tag`/`property_tag`; the gallery is `property_images` + `floor_plan_images`; the seed-on-first-use is `ensureDefaultUnitStatuses`; the nested-gallery sub-router is `properties.gallery` / `floorPlans.gallery`; the URL-backed sheet is `createOverlays`; the dual-mode picker is `TagPicker`. The server module (`router.ts` + `service.ts` + `schemas.ts`) is a statement-for-statement replication with the noun changed.

**The value is in the four deltas from those templates, each of which is a known trap:** (1) rename propagation (D-11) — the one place amenities diverge from tags, and getting it wrong silently reintroduces the drift the phase exists to prevent; (2) the gallery cap is **10, not 25** — but the existing `MAX_GALLERY_IMAGES` constant is a hard-coded `25` shared by two call sites in two packages, so amenities must NOT reuse it; (3) the units table needs **row selection + a bulk-action bar**, which the shared `DataTable` primitive does not currently expose at all; (4) migrations must be **hand-authored** because `drizzle-kit generate` is blocked by a corrupt snapshot chain (only 0000-0002, 0012, 0013 snapshots exist; 0014-0018 were all hand-written).

**Primary recommendation:** Replicate `modules/floor-plans/` (the freshest, cleanest analog) for the server module and `modules/tags/` for the catalog/promote/set semantics; introduce a phase-local `MAX_AMENITY_GALLERY_IMAGES = 10`; extract a parametrized gallery manager from `PropertyGalleryManager`; and treat the units-table row-selection wiring as the single largest UI risk (it likely requires extending `@villuh/ui`'s `DataTable`).

### Catalog↔assignment↔denormalization (copy `tags`, extend for rename)

`tags` gives you exactly:
- `attachOrganizationTag` → denormalize `label/iconKey/colorKey` from catalog at attach `[VERIFIED: tags/router.ts:158-179]`
- `setPropertyTags` → delete catalog-backed rows (`isNotNull(organizationTagId)`), re-insert from id array, **freeform untouched** — this is D-32 `set` `[VERIFIED: tags/router.ts:183-219]`
- `promoteFreeform` → dedupe by `(organizationId, name)`, link existing or insert `[VERIFIED: tags/router.ts:236-278]`

**D-11 rename propagation — the divergence.** `tags.updateOrganizationTag` `[VERIFIED: tags/router.ts:73-94]` patches ONLY the catalog row (leaves assignment labels stale). Amenities' `catalog.update` MUST, in the same `withOrganization` transaction, additionally:

```sql
-- pseudocode of the extra step D-11 requires
UPDATE property_amenity
   SET label = :newName, icon_key = :newIcon, color_key = :newColor
 WHERE organization_amenity_id = :id
   AND organization_id = :org
   AND label = :previousName;      -- only rows still carrying the old catalog name
-- identical UPDATE against unit_amenity
```
Read the previous name **before** patching the catalog row. Freeform rows (`organization_amenity_id IS NULL`) are excluded by the FK equality; deliberately customized per-property labels are excluded by the `label = previousName` guard.

### Seed pattern (mirror `ensureDefaultUnitStatuses`, but change the guard)

`ensureDefaultUnitStatuses(organizationId, tx)` lives in `apps/server/src/domain/unit-statuses.ts` and is invoked from `unitStatuses.list` on every read (idempotent). `[VERIFIED]` It uses `.onConflictDoNothing({ target: [org, name] })`.

**D-44 requires a DIFFERENT guard.** `ensureDefaultAmenities` must NOT rely on ON CONFLICT alone — it must first check "does this org have ANY `is_system` amenity, archived or not?" and skip entirely if so:
```
const [seeded] = await tx.select({ id: organizationAmenity.id })
  .from(organizationAmenity)
  .where(and(eq(org), eq(organizationAmenity.isSystem, true)))
  .limit(1)
if (seeded) return
// else insert the 22 rows
```
ON-CONFLICT-only would resurrect a starter amenity the moment a landlord archived it (archived rows keep their name, but a renamed archived row frees the name → duplicate). Place `ensureDefaultAmenities` in `apps/server/src/domain/amenities.ts` (or the module `service.ts`) and invoke from `amenities.catalog.list`.

## Common Pitfalls (LANDMINES — verified in the live tree)

### Pitfall 1: `MAX_GALLERY_IMAGES` is a shared hard-coded `25` — do NOT reuse it for the 10-cap
`[VERIFIED]` There are **two** constants, both `25`:
- `apps/server/src/modules/uploads/schemas.ts:7` → `export const MAX_GALLERY_IMAGES = 25` (server; used by `presignPropertyImage`, `presignFloorPlanImage`, and both `addGalleryImage` services)
- `packages/ui/utils/uploads.ts:66` → `export const MAX_GALLERY_IMAGES = 25` (client; default `atCapMessage`)

Amenities need **10**. Introduce a **new** server constant `MAX_AMENITY_GALLERY_IMAGES = 10` in `uploads/schemas.ts` and use it in `presignAmenityImage` + `amenities` `addGalleryImage`. On the client, pass the cap explicitly to `acceptImageFiles({ remainingSlots: 10 - images.length })` and to the gallery-manager `cap` prop — never rely on the `25` default message. Blindly reusing `MAX_GALLERY_IMAGES` ships a 25-cap amenity gallery and silently fails the SC-3 / spec §9.6 test.

### Pitfall 2: `drizzle-kit generate` is blocked — migration must be hand-authored
`[VERIFIED: migrations/meta/ contains only 0000,0001,0002,0012,0013 snapshots]` The journal (`_journal.json`) lists through 0018 but 0014-0018 have **no snapshots** — they were all hand-written. `0012_snapshot.json` id collides with root (STATE.md). Running `generate` will misbehave. **Hand-author `0019_amenities.sql`** following 0017/0018, append its entry to `_journal.json` (idx 19, `version: "7"`), and apply with the postgres-js migrator (`src/migrate.ts`, reads journal + `.sql` only — no snapshots needed). Do NOT attempt to repair the snapshot chain (deferred tech debt).

**Dual-DB apply (D-27a)** — `src/migrate.ts` reads `DATABASE_URL`. Apply to test DB by overriding it:
```bash
pnpm --filter @villuh/server migrate                                   # dev DB (DATABASE_URL)
DATABASE_URL="$DATABASE_OWNER_TEST_URL" pnpm --filter @villuh/server migrate   # test DB
```
A dev-only migrate leaves `amenities.test.ts` red with missing-column errors. `[VERIFIED: migrate.ts uses DATABASE_URL; setup.ts reads DATABASE_OWNER_TEST_URL / DATABASE_TEST_URL]`

### Pitfall 3: the shared `DataTable` has NO row-selection or bulk-bar API (biggest UI risk)
`[VERIFIED: packages/ui/src/data-table.tsx — DataTableProps has no rowSelection/onRowSelectionChange/enableRowSelection and no selection-action slot]` The underlying grid exports `DataGridTableRowSelect` / `DataGridTableRowSelectAll` primitives (re-exported at data-table.tsx:301-303), so selection is *possible* at the grid layer but **entirely unwired** in `DataTable`. D-41's "bulk action bar on row selection" therefore requires either (a) extending `@villuh/ui`'s `DataTable` with row-selection state + a selection-action-bar slot (touches the shared primitive — 3.1's freeze on it has now expired since 3.1 is complete, but this is a real, non-trivial change with cross-table blast radius), or (b) a units-only wrapper. **Flag this to the planner as the phase's largest unknown** (Open Q1). It is NOT a copy-paste like the rest of the phase.

### Pitfall 6: audit triggers are silent if omitted
Drizzle never emits them. Spec §9.11 tests audit rows on all four tables. Append four `CREATE TRIGGER <t>_audit … audit_log_trigger_fn()` to the migration (Phase 3 Pitfall 6, carried).

### Pitfall 7: the `both`-scope case must be tested on BOTH sides
