# Phase 03.3 Plan 02: Amenities Catalog API + Seed Summary

**Org amenity catalog `amenities.catalog.*` tRPC sub-router with rename propagation (D-11), archived-aware 22-entry seed (D-44), and promote-by-name dedupe (D-37), registered in appRouter and covered by an 8-case integration suite.**

## Performance

- **Duration:** ~15 min
- **Completed:** 2026-08-14
- **Tasks:** 3
- **Files modified:** 5 (4 created, 1 modified)

## Accomplishments
- `amenities.catalog.*`: list (seed-on-first-read), create, update, archive, restore, promoteFromProperty, promoteFromUnit — reads `protectedProcedure`, mutations `permissionProcedure('write')` (D-28), every body in `withOrganization` (RLS).
- Rename propagation (D-11): `catalog.update` captures `previousName`, patches the catalog row, then pushes `label`/`icon`/`color` onto property/unit assignments whose label still equals `previousName` — customized labels and freeform rows are untouched.
- `ensureDefaultAmenities`: seeds 22 `is_system` starter rows scoped property/both/unit (D-43); guards on ANY `is_system` row including archived (D-44), so a pruned/archived catalog never regrows.
- Promote dedupe (D-37): links the existing catalog row by name rather than creating a duplicate.
- `amenities.test.ts`: 8 green cases — cross-org isolation, name uniqueness → BAD_REQUEST, seed count, seed guard, rename propagation vs customized labels, archive-intact + restore, promote dedupe, and `organization_amenity` audit rows.

## Decisions Made
- Rename propagation only sets the fields actually changed by the caller (label when name changed; icon/color when those changed), matching D-11's intent — avoids clobbering assignment icon/color when only the name changes.
- Promoted catalog rows take the scope of the side they were promoted from (`property` / `unit`).

## Deviations from Plan
None - plan executed exactly as written. The §9.4/§9.7/§9.9 property-assignment cases were asserted here (not deferred to Plan 04) by inserting `property_amenity` rows directly through the RLS-enforced app connection via `withTestOrganization`, as the plan's Task 3 action permitted.

## Issues Encountered
- The `property_amenity_catalog_unique` partial index forbids two catalog-backed assignments to the same amenity on one property. The §9.4 rename test therefore places the matching-label and customized-label assignments on two different properties (both linked to the same catalog row) — this is the correct real-world shape and the test passes.
