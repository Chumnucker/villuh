<domain>
## Phase Boundary

An organization owns **one amenity catalog** whose entries are scoped `property`, `unit`, or `both`. Catalog entries are assigned to **properties** (with reservability config and a photo gallery of up to 10 images) and to **units** (individually from the unit form, or in bulk from a multi-row units-table selection). Assignments denormalize label/icon/color so display never requires a join and freeform (not-yet-promoted) rows render identically to catalog-backed ones. The goal is that amenity **labels stay consistent enough to filter and search on** instead of drifting into unmatchable free text ("W/D in unit" vs "Washer/Dryer" vs "washer dryer").

Four tables ship this phase: `organization_amenity` (catalog), `property_amenity` (assignment), `unit_amenity` (assignment), `property_amenity_image` (gallery). A fifth table (`amenity_reservation`) and its two enums/constraints are **designed in the spec but NOT built here**.

**Explicitly out of this phase's build:**
- **Reservations** — the `amenity_reservation` table, `amenity_reservation_status` enum, overlap exclusion constraint, approval queue, `/reservations` sidebar surface, and all reservation UI. Deferred to a phase after Phase 4 (needs `tenants` and a resident request surface). `is_reservable` / `requires_approval` config columns on `property_amenity` **do** ship now; nothing reads them yet.
- **Resident portal** (`apps/resident-web`) — no amenity surface. The data model + read procedures support it as a future consumer; building it is not in scope.
- **Floor-plan amenity inheritance** — unit amenities attach directly to units; bulk-apply solves the many-units problem. A later `floor_plan_amenity` + read-time merge is purely additive.
- **Deferred `property_amenity` reservation-config columns** (`min_duration_minutes`, `max_duration_minutes`, open hours, advance-notice window, capacity) — land with the reservations phase.

</domain>

## Implementation Decisions

Decision numbering mirrors the spec's §3 table (D-01…D-14 = spec D-1…D-14), plus phase-specific additions (D-15+).

### Scope & sequencing

- **D-01:** Full amenities domain is specced now; **catalog + property assignments + unit assignments + property gallery are built now; reservations are built in a later phase** (after Phase 4). Reservations need `tenants` (Phase 4, not started) and a resident-portal request surface.
- **D-15 (sequencing):** Phase 3.3 has a **hard gate on Phase 3.1 (URL query state) — which is COMPLETE**. The units amenities column lives in `units-columns.tsx` / the units table, which 3.1 forbade modifying while in flight (3.1 D-05, D-28). The amenity detail sheet MUST be declared via 3.1's `createOverlays('amenity', …)` (URL-backed, cold-loads open by id); any reservations table (later phase) uses `defineTable`. **Do not add `useState` overlay trios** — 3.1 deleted that pattern.
- **D-16 (sequencing):** Soft dependency on Phase 3.2 (Floor Plans) — **no shared files**. 3.3 may be planned and executed independently; the only overlap is the gallery-manager generalization (see D-31), which reuses 3.2's work if present.

### Catalog table — `organization_amenity`

- **D-02:** **One `organization_amenity` catalog with `scope = property | unit | both`**, plus **separate `property_amenity` and `unit_amenity` assignment tables**. Catalog fields are identical for both kinds; assignment fields are not (reservability and galleries are property-only). `both` prevents duplicate catalog rows for air conditioning / parking / laundry, which are legitimately either.
- **D-17 (table shape):** `organization_amenity` columns: `id uuid PK default gen_random_uuid()`, `organizationId text NOT NULL` → `organization.id` `onDelete: 'cascade'`, `name text NOT NULL`, `description text` (nullable), `scope amenity_scope NOT NULL`, `iconKey amenity_icon NOT NULL default 'IconStar'`, `colorKey tag_color NOT NULL default 'slate'`, `isSystem boolean NOT NULL default false`, `sortOrder integer NOT NULL default 0`, `archivedAt timestamptz` (nullable), `createdAt`/`updatedAt timestamptz NOT NULL default now()`. Constraints: `unique('organization_amenity_org_name_unique').on(organizationId, name)` and the `organization_isolation` `pgPolicy` identical to `organization_tag`, `.enableRLS()`.
- **D-10:** **Catalog archives, never deletes** (`archivedAt`). Tags cascade-delete assignments; deleting "Pool" must not silently strip the pool and its photos from eight properties. Archiving hides an entry from pickers while every existing assignment keeps rendering unchanged.
- **D-12:** **Icon and color are `NOT NULL` with defaults, not nullable.** Optional in the UI, never null in the DB — nullable would push a fallback into every render site (card, chip, sheet header, resident portal, listing feed) and they would disagree.
- **D-18 (`isSystem` semantics):** `isSystem` marks **seed provenance only** — system rows are freely renamable, re-iconable, and archivable.

### Enums

- **D-04:** New **`amenity_icon` Postgres enum (~38 curated Solar Linear icon keys)**; **reuse the existing 8-value `tag_color` enum**. The locked 14-icon tag palette has no pool/gym/laundry/wifi, so every amenity would become a star and the icon would carry no information. Enum keys and their `PlatformIcon` → `@solar-icons/react/linear` mappings are the 38-key table in spec §5.1 (`IconStar` default, `IconPool`→swimming, `IconGym`→dumbbell, `IconLaundry`→washing-machine, `IconWifi`→wi-fi-router, … `IconLibrary`→book). Each enum is a `pgEnum` built from the same `as const` array (`AMENITY_SCOPES`, `AMENITY_ICON_KEYS`) that backs its Zod validator, per the project enum convention.
- **D-19 (icon verification):** Every one of the 38 `AMENITY_ICON_KEYS` must map to a **verified** existing `@solar-icons/react/linear` icon through `PlatformIcon`. Any Solar name in the spec table that does not resolve must be corrected to a real Solar Linear icon during planning/execution — an unresolved key renders nothing. `PlatformIcon` keeps Central-style keys mapped to Solar equivalents (Phase 03 icon-library decision).
- **D-20 (reservation-status enum deferred):** `amenity_reservation_status` (`pending | approved | denied | cancelled`) is **NOT created this phase** — nothing reads it before reservations ship.

### Assignment table — `property_amenity`

- **D-21 (table shape):** `property_amenity` columns: `id uuid PK`, `organizationId text NOT NULL` → cascade, `propertyId uuid NOT NULL` → `properties.id` `onDelete: 'cascade'`, `organizationAmenityId uuid` **nullable** → `organization_amenity.id` `onDelete: 'set null'` (null = freeform, not yet promoted), `label text NOT NULL`, `description text`, `iconKey amenity_icon NOT NULL default 'IconStar'`, `colorKey tag_color NOT NULL default 'slate'`, `isReservable boolean NOT NULL default false`, `requiresApproval boolean NOT NULL default true`, `sortOrder integer NOT NULL default 0`, `createdAt`/`updatedAt timestamptz NOT NULL default now()`, plus `organization_isolation` RLS + `.enableRLS()`.
- **D-22 (partial unique index):** `CREATE UNIQUE INDEX property_amenity_catalog_unique ON property_amenity (property_id, organization_amenity_id) WHERE organization_amenity_id IS NOT NULL;` — blocks attaching the same catalog amenity twice while leaving freeform rows unconstrained (two custom entries on one property are legitimate).
- **D-05:** **Reservation config (`is_reservable`, `requires_approval`) lives on `property_amenity`, not the catalog** — one building's pool is bookable, another's is not.
- **D-23 (denormalization):** `label`, `icon_key`, `color_key` are denormalized so display never needs a join and freeform rows render identically to promoted ones (the `property_tag` pattern).

### Assignment table — `unit_amenity`

- **D-24 (table shape):** Deliberately thinner than `property_amenity`: `id`, `organizationId` (→ cascade), `unitId uuid NOT NULL` → `units.id` `onDelete: 'cascade'`, `organizationAmenityId uuid` nullable → `organization_amenity.id` `onDelete: 'set null'`, `label text NOT NULL`, `iconKey amenity_icon NOT NULL default 'IconStar'`, `colorKey tag_color NOT NULL default 'slate'`, `createdAt timestamptz NOT NULL default now()`, the equivalent partial unique index on `(unit_id, organization_amenity_id) WHERE organization_amenity_id IS NOT NULL`, and the `organization_isolation` RLS policy. **No description, no gallery, no reservability, no `updatedAt`, no `sortOrder`.** A photo of a faucet is not useful; the catalog description explains a unit amenity if needed.
- **D-03:** **Unit amenities attach to units, with bulk-apply from the units table.** Floor-plan inheritance is deferred (purely additive later).

### Gallery table — `property_amenity_image`

- **D-25 (table shape):** Mirrors `property_images` exactly: `id`, `organizationId` (→ cascade), `propertyAmenityId uuid NOT NULL` → `property_amenity.id` `onDelete: 'cascade'`, `objectKey text NOT NULL`, `contentType text NOT NULL`, `byteLength integer NOT NULL`, `sortOrder integer NOT NULL default 0`, `createdAt timestamptz NOT NULL default now()`, RLS policy. **No `updatedAt`, no soft delete.**
- **D-26 (gallery rules):** `object_key` only, never a URL — presigned GET generated at read time. **Cap = 10 images** per amenity, the 11th refused **server-side in both the presign procedure and `gallery.add`** (belt-and-braces, mirroring the property 25-cap). Rows are hard-deleted with their S3 object. First image by `sort_order` is the cover. S3 key nests under the parent property, mirroring the floor-plan pattern (e.g. `{org}/properties/{propertyId}/amenities/{propertyAmenityId}/gallery/{uuid}.{ext}`; final key layout confirmed against `presignPropertyImage` during planning).

### Migration

- **D-27 (migration):** Four tables + two enums (`amenity_scope`, `amenity_icon`) generated with `drizzle-kit generate`, then **hand-appended** with an audit trigger per table (Drizzle does not emit them):
  ```sql
  CREATE TRIGGER organization_amenity_audit AFTER INSERT OR UPDATE OR DELETE ON organization_amenity
    FOR EACH ROW EXECUTE FUNCTION audit_log_trigger_fn();
  -- …and for property_amenity, unit_amenity, property_amenity_image
  ```
  The generated SQL MUST be **read before applying** to confirm all four `ENABLE ROW LEVEL SECURITY` statements, all four `organization_isolation` policies, the `organization_amenity` unique constraint, and both partial unique indexes (D-22, D-24) are present. Omitting an audit trigger is silent (Phase 3 Pitfall 6).
- **D-27a (dual-DB apply):** Migrations must be applied to **both** the dev DB (`DATABASE_URL`) **and** the test DB (`DATABASE_OWNER_TEST_URL`) — the server test suites run against `villuh_test`, so a dev-only migrate leaves them red with missing-column errors (carried from Phase 03.2-01). If `drizzle-kit generate` is blocked by the pre-existing corrupt snapshot chain (noted in STATE.md), the migration is hand-authored following the 03.2 `0017` precedent; the migrator reads journal + `.sql` only.

### API

- **D-09:** **Own module `modules/amenities/`** on both server (`apps/server/src/modules/amenities/`) and frontend (`apps/landlord-web/modules/amenities/`). Amenities span properties, units, the org catalog, and a later cross-property surface; placing them in `modules/properties/` (as floor plans are) would force `modules/units/` to import from `modules/properties/`.
- **D-28 (router shape):** One `amenities` router with nested sub-routers (following the pattern `properties` uses for its nested `gallery`):
  ```
  amenities: {
    catalog:  { list, create, update, archive, restore, promoteFromProperty, promoteFromUnit },
    property: { list, add, addFreeform, update, remove, reorder, set,
                gallery: { list, add, reorder, remove } },
    unit:     { list, listByProperty, set, addFreeform, remove, bulkAdd, bulkRemove },
  }
  ```
  Reads = `protectedProcedure`; **every mutation = `permissionProcedure('write')`**; every body runs inside `withOrganization(organizationId, userId, …)`.
- **D-29 (presign placement):** `uploads.presignAmenityImage` joins the other presigners in the `uploads` module (alongside `presignPropertyImage` / `presignFloorPlanImage`), enforces the 10-image cap before returning a URL; the row is created afterward by `amenities.property.gallery.add`.
- **D-30 (schema export):** Zod schemas live in `apps/server/src/modules/amenities/schemas.ts`, exported as `@villuh/server/schemas/amenities` via a **new `"./schemas/amenities"` entry in `apps/server/package.json` exports** (without it the import resolves under the tsconfig alias but fails at runtime — the 03.2 D-23 lesson), imported directly by frontend forms. No duplicated validation.
- **D-32 (update vs set semantics — easy to conflate):**
  - **`property.update`** patches ONE assignment (`label`, `description`, `iconKey`, `colorKey`, `isReservable`, `requiresApproval`). It never touches the catalog row.
  - **`property.set` / `unit.set`** bulk-replace a property's/unit's **catalog-backed** assignments from an id array (mirroring `tags.setPropertyTags`), leaving **freeform rows untouched**. These back multi-select in the picker; `add` / `addFreeform` / `remove` back single-item interactions.
- **D-33 (bulk ops):** `unit.bulkAdd` takes `unitIds[] × organizationAmenityIds[]` and performs **one** insert with `ON CONFLICT … DO NOTHING` against the partial unique index — re-applying to 40 units where 12 already have it is one round trip, silently idempotent, not 40 requests + 12 errors. Scope validated once for the whole batch. `bulkRemove` is a single delete. `unit.listByProperty` exists so the units table renders + filters an amenities column in one query, not one per row.

### Server-side validation (§6.1 — none of this is trusted from the client)

- **D-34 (scope enforcement):** A `unit`-scoped catalog item cannot be attached to a property, and vice versa; `both` permits either. Reject with `BAD_REQUEST`.
- **D-35 (ownership):** The target property/unit must belong to the caller's organization — RLS covers cross-org, but an explicit 404 beats an opaque zero-row result.
- **D-36 (cross-entity):** An assignment id must belong to the property/unit named in the input (reject cross-property / cross-unit).
- **D-37 (promote dedupe):** `promoteFrom*` matches an existing catalog row **by name** rather than creating a second "Rooftop deck", and links the assignment to the existing row.

### Rename propagation & invalidation

- **D-11:** **`catalog.update` propagates `label`/`icon_key`/`color_key` to assignment rows whose label still equals the catalog's previous name**, in the same transaction. Diverges from `tags.updateOrganizationTag` (which leaves stale labels behind — reintroducing the exact drift the catalog prevents). Scoping by previous name preserves deliberately customized per-property labels without an override column. Freeform rows (null FK) are untouched.
- **D-13:** **Amenities are not plan-limited; `syncOrgUnitQuantity` is untouched.** Amenities are metadata, not billable entities. No `PLAN_RESOURCES` change, no `me.get` quota field.
- **D-38 (invalidation contract — per ADR-001, via `invalidateOnSuccess`/`invalidateQueries`):**
  - Catalog mutations → `catalog.list`, `property.list`, **and** `unit.list` (necessary because of rename propagation, D-11).
  - Property assignment mutations → `property.list` + `properties.get` (About tab chips).
  - Unit assignment mutations → `unit.list`, `unit.listByProperty`.
  - Gallery mutations → `property.gallery.list` + `property.list` (photo counts).
  - **Nothing touches `me.get` quotas or the Stripe unit-quantity sync** (D-13).

### UI

- **D-39 (settings page):** Replace the placeholder `property-settings-amenities-template.tsx`. Two sections, deliberately unequal in weight:
  - **"Property amenities"** — a card grid of this property's amenities. Each card: colored icon tile, name, description snippet, "Reservable" badge when applicable, photo count. Clicking a card opens the amenity sheet. "Add amenity" uses the **search-or-create popover pattern from `TagPicker`** (find in catalog or create inline).
  - **"Amenity catalog"** — compact read-only chips grouped by scope, with **"Manage catalog…"** in the section's `action` slot opening `ManageAmenityCatalogDialog` — the same convention `property-settings-units-template.tsx` uses for its "Unit statuses" button.
- **D-40 (amenity sheet):** Declared through **3.1's `createOverlays('amenity', …)`** so it is URL-backed and a link cold-loads with the sheet open, fetching by id. Header: icon tile, name, reservable state. Body: editable details + gallery manager (+ later, a reservation history section — no sheet change required to add it).
- **D-41 (units):** `AmenityPicker` in `UnitFormSheet` — a **near-twin of `TagPicker`**, same **dual-mode** design (staged local array during unit create, live tRPC mutations once a `unitId` exists), filtered to `unit | both` scope. Units `DataTable`: **amenities column with chip overflow**, plus a **bulk action bar on row selection** offering add and remove (`unit-amenities-bulk-actions.tsx`).
- **D-14:** **Remove the tags-as-amenities stopgap from the property About tab.** The About tab renders **real** amenities as a read-only chip row. `TagBadge` already accepts a color-key variant and both palettes share `tag_color`, so no new primitive is needed. Two overlapping ways to say a property has a pool will drift — so the stopgap is deleted, not left alongside.
- **D-31 (gallery-manager refactor — in scope):** `modules/properties/components/settings/gallery-manager.tsx` is currently property-specific. By the time amenities ship there are three galleries: property (existing), floor plan (3.2, 25), amenity (10). Three copies of drag-reorder-plus-presigned-upload is two too many. **If 3.2 already generalized it, amenities reuse it unchanged. If not, extract here:** a `GalleryManager` taking list/add/reorder/remove callbacks + a cap, with three call sites passing their own tRPC procedures. (Planner MUST inspect the current 3.2 state to decide reuse vs extract.)
- **D-42 (new frontend files, per spec §7.6):**

  modules/amenities/components/amenity-picker.tsx              — dual-mode picker (staged / live), scope-filtered
  modules/amenities/components/amenity-icon-color-picker.tsx   — 38-icon scrollable grid + 8 colors
  modules/amenities/components/manage-catalog-dialog.tsx       — org catalog CRUD (create / edit / archive / restore)
  modules/amenities/components/amenity-card.tsx                — settings grid card
  modules/amenities/components/amenity-sheet.tsx               — detail overlay
  modules/amenities/components/amenity-chip-row.tsx            — read-only display (About tab, unit detail)

### Seeded starter catalog

- **D-43 (seed):** `ensureDefaultAmenities` (following the `ensureDefaultUnitStatuses` pattern) seeds **22 entries with `is_system = true` on first use**:

### Testing & verification

- **D-45 (server integration tests):** New `apps/server/src/__tests__/amenities.test.ts` following the `properties.test.ts` shape (`setupOwner`, direct tRPC caller, no HTTP), covering spec §9: (1) cross-org isolation on all four tables; (2) catalog `(organization_id, name)` uniqueness; (3) scope enforcement — unit-scoped rejected on a property and vice versa, `both` accepted on either; (4) rename propagation updates matching labels **and leaves customized labels untouched**; (5) bulk apply idempotent via the partial unique index (40 units, 12 pre-existing → no error, no dupes); (6) gallery cap — 11th image refused; (7) archiving a catalog item leaves assignments intact and rendering unchanged; (8) seed guard does not resurrect archived system rows; (9) promote dedupes by name and links the existing row; (10) cross-property / cross-unit assignment ids rejected; (11) audit trigger rows written for all four tables.

## Existing Code Insights

### Reusable Assets
- **The tags system is the closest analog for the whole catalog↔assignment↔denormalization model.** `organization_tag`/`property_tag`, `TagPicker` (search-or-create, dual-mode), `TagBadge` (shared `tag_color`), `setPropertyTags` (id-array replace), and freeform-then-promote all map directly onto amenities. The catalog is what tags *lacks* — an org-level entity that assignments reference — so amenities = tags + a catalog layer + scope + galleries + reservability.
- **The property gallery is a complete working template** for the amenity gallery (10-cap variant): table shape, presign → browser `PUT` → `gallery.add`, double-enforced cap, index reorder, S3-delete-then-row-delete. Floor plans (3.2) already replicated it once at a 25-cap; amenities do it again at 10 — strong signal to generalize (D-31).
- **`ensureDefaultUnitStatuses`** is the exact seed-on-first-use pattern for `ensureDefaultAmenities` (D-43/D-44).
- **`createOverlays` (3.1)** makes the amenity sheet URL-backed for free (D-40); **`defineTable` (3.1)** is ready for the later reservations table.
- **`persistStagedGallery` already takes injected callbacks** (3.2 dropped its explicit `propertyId`), so retargeting it at an amenity gallery is a signature reuse, not a rewrite.

## Specific Ideas

- **The catalog's entire value is label consistency, not keystroke saving.** Every design choice (freeform-then-promote, seed-on-first-use, rename propagation) exists so an amenity stays queryable across properties. If the implementation makes the catalog costly to maintain, landlords bypass it and the drift returns.
- **Rename propagation (D-11) is the single most important divergence from tags.** Copy the `updateOrganizationTag` shape but add the "update assignments whose label still equals the previous name" transaction step. Getting this wrong silently reintroduces the drift the whole phase exists to prevent.
- **Denormalize label/icon/color onto assignments (D-23) so freeform and catalog-backed rows render identically** — the display layer must never branch on "has a catalog FK or not."
- **`is_reservable` / `requires_approval` ship as columns now but nothing reads them** — they are inert config until the reservations phase. Do not build any reservation behavior.
- **The seed guard checks archived system rows too (D-44)** — a landlord who deletes half the starter catalog must not have it silently regrow.
- **Bulk apply must be one idempotent query (D-33)**, not N requests — this is the design's answer to the 200-unit problem in place of floor-plan inheritance.
- **Amenity `both`-scope entries must be attachable to either a property or a unit** — scope enforcement (D-34) permits `both` on both sides; test it explicitly.

### Suggested wave shape (planner may revise)
1. **Enums + schema + migration** — `amenity_scope`, `amenity_icon`, all four tables, RLS, both partial unique indexes, four audit triggers, journal; applied to dev + test DBs. Blocking.
2. **Catalog API + seed** — `amenities.catalog.*`, `ensureDefaultAmenities`, rename propagation, promote dedupe; `amenities.test.ts` (catalog/isolation/uniqueness/seed-guard/promote).
3. **Property assignment API + gallery** — `amenities.property.*` incl. nested `gallery.*`, `uploads.presignAmenityImage` (10-cap); scope/ownership/cross-entity validation; gallery-cap test.
4. **Unit assignment API** — `amenities.unit.*` incl. `bulkAdd`/`bulkRemove`/`listByProperty`; bulk-idempotency + cross-unit tests. (Parallel-ish with 3.)
5. **`amenity-icons.ts` + shared UI primitives** — palette constants + `PlatformIcon` mapping (verify all 38 keys), `amenity-icon-color-picker`, `amenity-chip-row`, `AmenityPicker`; gallery-manager reuse/extract decision (D-31). Depends on 2–4.
6. **Property settings UI** — settings template replacement, `amenity-card`, `manage-catalog-dialog`, `amenity-sheet` via `createOverlays`. Depends on 5.
7. **Unit UI + About tab** — `AmenityPicker` in `UnitFormSheet`, units-table amenities column + `unit-amenities-bulk-actions`, About tab real chips + stopgap removal (D-14). Depends on 4, 5, and the 3.1-migrated units table.

### Verification (must be demonstrated, not assumed — spec §9 + success criteria)
- Create/rename/re-icon/archive a catalog amenity; archived entry leaves pickers but every existing assignment still renders unchanged.
- Rename a catalog amenity → assignments still carrying the old name update; a deliberately customized per-property label is left untouched.
- Attach catalog + freeform amenities to a property; mark one reservable + requires-approval; upload up to 10 photos, confirm the 11th is refused server-side; promote a freeform entry without creating a by-name duplicate.
- Assign unit amenities from the unit form and in bulk from a multi-row units-table selection; re-apply to units that already have them → idempotent, no error, no dupes.
- A `unit`-scoped amenity is rejected server-side on a property (and vice versa); `both` accepted on either.
- Cross-organization access blocked by RLS; the amenity detail sheet cold-loads open from a pasted URL.
- The property About tab renders real amenities; the tag-based stopgap is gone.
- Audit rows written for all four tables.
