# Phase 03.3 Plan 08: Units Amenities Surface Summary

Opt-in row selection + a selection-action-bar slot were added to the shared `DataTable` (additive, default-off), then used to ship the units amenities surface: an `AmenityPicker` in the unit form (staged on create, live on edit), a chip-overflow amenities column fed by one `listByProperty` query per property, and a `UnitAmenitiesBulkActions` bar wiring `bulkAdd`/`bulkRemove` as one idempotent call each (SC-4).

## What Was Built

### Task 1 — DataTable opt-in row selection (`bad3f4a`)
`DataTableProps` gained four optional members: `enableRowSelection?`, `rowSelection?` + `onRowSelectionChange?` (controlled; internal state otherwise), and a `selectionActions?: (ctx: { selectedRowIds, clearSelection }) => ReactNode` render slot. When `enableRowSelection` is falsy — every existing call site — no checkbox column is prepended, no selection state is added to the table instance, and the bar never renders, so other tables are byte-behavior-unchanged (T-033-20, Open Q1 resolved to additive extend). When on, a leading `select` column is prepended using the already-exported `DataGridTableRowSelectAll`/`DataGridTableRowSelect` primitives and `@tanstack/react-table`'s `state.rowSelection` / `onRowSelectionChange` / `enableRowSelection` are wired.

### Task 2 — unit form picker + amenities column (`9051e21`)
- `unit-form-sheet.tsx`: an `AmenityPicker` field renders staged (`context="unit"`, `value`/`onChange`) during create and live (`unitId`) in edit. Staged rows persist right after `units.create` returns an id — catalog rows via one `amenities.unit.set`, freeform rows via `addFreeform` — then invalidate `units.list` + `amenities.unit.listByProperty` + `properties.get` + `me.get` (D-38/D-41). `me.get` retained only for the existing unit-quota; no new `me.get` amenity dependency (D-13).
- `columns.tsx`: a non-sortable `amenities` column renders `AmenityChipRow` with `max={3}` overflow, keyed off a per-page `amenitiesByUnit` map (em-dash placeholder while loading).
- `index.tsx`: the map is built from `amenities.unit.listByProperty` issued once per DISTINCT property on the current page via `trpc.useQueries` (one query for a property-scoped table; bounded by property count otherwise — never per row, D-33).

### Task 3 — bulk-actions bar + selection wiring (`d10e361`)
`UnitAmenitiesBulkActions` takes `{ selectedUnitIds, clearSelection }`, offers a scope-filtered (unit|both) catalog multi-select, and Add/Remove each fire ONE `amenities.unit.bulkAdd`/`bulkRemove` with `{ unitIds, organizationAmenityIds }` (D-33). Re-adding where some units already have the amenity is a server no-op (idempotent), then it invalidates `amenities.unit.list` + `listByProperty` + `units.list` (D-38) and clears the selection. The units `DataTable` turns on `enableRowSelection` + `getRowId={(u) => u.id}` and passes the bar through `selectionActions`. The client scope filter is UX only; the server re-enforces scope + org on the batch (T-033-21).

## Deviations from Plan

**None affecting scope.** Two clarifications:
- **Amenities-column data source, global list.** The plan's interface note assumed a single `listByProperty` query. The `/units` list can span properties, so the map is assembled from one `listByProperty` per DISTINCT property on the current page (via `trpc.useQueries`). This preserves D-33's "no query per row" intent while working on both the global list and the property-scoped Units tab.
- **Staged-persist moved into `onSubmit`.** `createUnit.onSuccess` no longer toasts/closes; success handling (staged-amenity persistence → invalidation → toast → close) lives in the form `onSubmit` after `mutateAsync` returns the new id, matching `PropertyForm`. This was required so the staged amenities persist before the sheet closes.
