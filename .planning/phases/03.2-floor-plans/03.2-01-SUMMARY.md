## Accomplishments
- `floor_plans` table live with `id`, `organization_id`, `property_id` (FK → properties, cascade), `name`, `bedrooms` (int NOT NULL), `bathrooms` (numeric(4,2) NOT NULL, JS number), `default_square_footage` (nullable), `archived_at`, `created_at`, `updated_at`, plus the `floor_plans_property_name_unique` per-property unique constraint (D-05, D-09).

- Migration `0017_floor_plans.sql` applied cleanly to both the dev DB (`DATABASE_URL`) and the test DB (`villuh_test` via `DATABASE_OWNER_TEST_URL`).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Hand-authored the migration because `drizzle-kit generate` is blocked by a pre-existing corrupt + stale snapshot baseline**
- **Found during:** Task 2, step 1 (`pnpm --filter @villuh/server run generate`).
- **Issue (two independent pre-existing defects):**
  1. **Chain collision:** `migrations/meta/0012_snapshot.json` has its `id` set to the all-zeros root sentinel (`00000000-0000-0000-0000-000000000000`). `0013_snapshot.json.prevId` then equals all-zeros too, so drizzle-kit sees both `0000` and `0013` as roots and aborts: *"...are pointing to a parent snapshot ... which is a collision."*
  2. **Stale baseline:** the latest committed snapshot is `0013`, but migrations `0014` (audit partitions), `0015` (property_type/year_built/parking) and `0016` (enum types) were themselves hand-written with **no** snapshot files. `0013_snapshot.json` therefore lacks `property_type`, `parking_type`, and all enum types — so even after fixing the chain, `generate` would emit large out-of-scope churn (re-adding columns/enums that already exist live) and could fail at migrate time.
- **Fix:** Hand-authored `apps/server/migrations/0017_floor_plans.sql` mirroring the `0013_pink_azazel.sql` DDL shape exactly (CREATE TABLE → ENABLE RLS → ADD COLUMN → ADD CONSTRAINT FKs → CREATE POLICY → hand-appended audit triggers with `--> statement-breakpoint` between and none trailing), added the `0017_floor_plans` entry to `_journal.json`, and applied via the standard `migrate` script. This matches how `0014`-`0016` were produced. The Drizzle migrator reads the journal + `.sql` files only, so `migrate` is unaffected by the broken snapshots.
- **Scope decision:** did NOT repair the `0012`/`0013` snapshot chain or fabricate a `0017_snapshot.json` — both would either be out of scope or perpetuate the baseline drift by chaining off a snapshot that misrepresents the live DB. Logged as pre-existing tech debt in `deferred-items.md`.
- **Files:** `apps/server/migrations/0017_floor_plans.sql` (new), `apps/server/migrations/meta/_journal.json` (modified).
- **Commit:** `b91657c`.

**2. [Rule 3 - Blocking] Applied the migration to the test database as well as the dev database**
- **Found during:** Task 2 verification (`vitest run units.test.ts`) — failed with `column "floor_plan_id" of relation "units" does not exist`.
- **Issue:** `run migrate` applies to `DATABASE_URL` (dev DB) only, but the server suites run against a separate `villuh_test` DB (`DATABASE_TEST_URL`/`DATABASE_OWNER_TEST_URL`). The updated ORM schema emitted an INSERT referencing the new columns, which the un-migrated test DB rejected.
- **Fix:** Re-ran the migrator against the test DB by overriding `DATABASE_URL` with `DATABASE_OWNER_TEST_URL` (Node `--env-file` and dotenv both defer to a pre-set env var). No code change.
- **Files:** none (DB state only).
- **Verification:** all three suites (23 tests) pass afterward.

**Total deviations:** 2 auto-fixed, both Rule 3 blocking issues in the migration tooling/environment, not application logic.
