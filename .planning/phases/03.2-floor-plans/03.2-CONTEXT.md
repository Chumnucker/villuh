# Phase 3.2: Floor Plans - Context

**Gathered:** 2026-08-13
**Status:** Ready for planning
**Type:** INSERTED (decimal phase after Phase 3.1)

<domain>
## Phase Boundary

A property owns a set of **floor plans** — reusable unit layouts carrying a name, bedroom count, bathroom count, an optional default square footage, and a gallery of up to 25 images. A unit may be assigned one floor plan of its own property, and then inherits that plan's numbers unless the unit explicitly overrides them. Floor plans are created and edited through a **new wizard-style dialog variant** in `@villuh/ui` — a wide, two-column overlay with a left sidebar (title, description, vertical stepper) and a much larger right content pane — which is built once here as a general-purpose primitive and used first by floor plans.

Two things ship together because one is the vehicle for the other: the `WizardDialog` primitive in `packages/ui`, and the floor plans feature (schema, tRPC module, settings UI, unit assignment).

**Explicitly out of this phase's build:** rent on floor plans (rent calculation strategy is undecided — see Deferred), cross-property or organization-level plan reuse, bulk-assigning units from the plan's side, a standalone floor plan detail page or route, plan-tier quotas on floor plan count, and any resident-web surface.

</domain>

<decisions>
## Implementation Decisions

### Scope & sequencing

- **D-01:** Phase 3.2 sequences **after Phase 3.1 (URL query state)**. The floor plan wizard is a brand-new overlay, so it is registered in the properties module's overlay config from birth (`createOverlays` per 03.1 D-07/D-31) and spreads `overlay.dialogProps` onto `WizardDialog`. Building it before 03.1 would mean writing `useState` plumbing and immediately migrating it.
- **D-02:** The overlay param carries the payload only — `new` for creation, a floor plan id for editing (03.1 D-05). **The active wizard step is NOT in the URL.** A half-completed creation form is not meaningfully shareable and its state would be a lie on cold load (03.1 D-16 — URL-ify only what a user could link to or expect back to undo).
- **D-03:** Floor plans are **property-scoped**: `propertyId` is a non-null FK with `onDelete: 'cascade'`. A landlord with three identical buildings re-creates the plan per property in v1. Org-level reuse is deferred, not designed against.
- **D-04:** **Rent is not a floor plan field.** No `baseRent`, no rent defaults, no rent inheritance. Units keep their existing `baseRent` untouched by this phase.

### Data model — `floor_plans`

- **D-05:** New table `floor_plans`, following the org-scoped tenant table pattern exactly: `id uuid PK default gen_random_uuid()`, `organizationId text NOT NULL` → `organization.id` cascade, `propertyId uuid NOT NULL` → `properties.id` cascade, `name text NOT NULL`, `bedrooms integer NOT NULL`, `bathrooms numeric(4,2) NOT NULL`, `defaultSquareFootage integer` (nullable), `archivedAt timestamptz` (nullable), `createdAt`/`updatedAt timestamptz NOT NULL default now()`, plus the `organization_isolation` `pgPolicy` and `.enableRLS()`.
- **D-06:** **Name, bedrooms and bathrooms are required; default square footage is optional.** A plan with no bed/bath counts cannot do its only job, so requiring them is correct. Square footage is the number that genuinely drifts per unit (the stated 10–20 sq ft variance), so a landlord is allowed to leave the plan-level default blank and let each unit carry its own.
- **D-07:** `bathrooms` is `numeric(4,2)` supporting **quarter increments** (1.25 / 1.5 / 1.75), validated in Zod as `multipleOf(0.25)`, `min(0)`, `max(20)`. Precision 4 (not 3) because scale 2 with precision 3 caps at 9.99, and 10+ bath layouts must remain expressible. **Verify during planning** that `drizzle-orm@0.45.2` supports `numeric(..., { mode: 'number' })`; if it does not, the column returns a string and the service layer must coerce at both read and write boundaries — either way, the tRPC contract exposes a `number`.
- **D-08:** `bedrooms` is a plain `integer`, `min(0)`, `max(20)`, where **0 renders as "Studio"** in the UI. It is not a Postgres enum: it is an open numeric range, not a closed option set the app owns.
- **D-09:** Plan names are **unique per property** — `unique('floor_plans_property_name_unique').on(organizationId, propertyId, name)` — mirroring the existing `unit_statuses_org_name_unique`. A collision surfaces as a field-level error on the wizard's name input, not a toast.
- **D-10:** **No `sortOrder` column.** Floor plans are listed alphabetically by name. Manual ordering is unrequested complexity (YAGNI).
- **D-11:** Archiving is **soft** (`archivedAt`) and **does not cascade to units**. An archived plan disappears from assignment pickers but assigned units keep pointing at it and keep inheriting its values. Blanking out forty units' bed counts because someone tidied a list is unacceptable data loss, and this matches how properties and units already soft-delete.

### Data model — `floor_plan_images`

- **D-12:** New table `floor_plan_images`, a deliberate near-copy of `property_images`: `id`, `organizationId`, `floorPlanId uuid NOT NULL` → `floor_plans.id` cascade, `objectKey text NOT NULL`, `contentType text NOT NULL`, `byteLength integer NOT NULL`, `sortOrder integer NOT NULL default 0`, `createdAt timestamptz NOT NULL`, plus `organization_isolation` RLS. **No `updatedAt`** and **no soft delete** — rows are hard-deleted alongside their S3 object, exactly as gallery rows are today (Phase 3 D-37).
- **D-13:** **No denormalized `propertyId` column.** Every code path already loads the parent plan row to authorize the operation, and that row carries `propertyId`.
- **D-14:** The cap is the **existing `MAX_GALLERY_IMAGES = 25`** constant reused verbatim, enforced server-side in **both** the presign procedure and the add procedure — the same belt-and-braces the property gallery uses. It is a fixed product rule, not a billing lever.
- **D-15:** `sortOrder` 0 is the **cover image**; reorder takes a full ordered `imageIds` array and renumbers by index. Identical semantics to `properties.gallery.reorder`.
- **D-16:** S3 object keys are `{organizationId}/properties/{propertyId}/floor-plans/{floorPlanId}/gallery/{uuid}.{ext}`. Only the `objectKey` is persisted; presigned GET URLs are attached at read time and never stored.

### Data model — `units` additions

- **D-17:** Three columns added to `units`: `floorPlanId uuid` → `floor_plans.id` **`ON DELETE SET NULL`** (identical treatment to the existing `statusId`), `bedrooms integer` (nullable), `bathrooms numeric(4,2)` (nullable). `squareFootage integer` already exists and is already nullable.
- **D-18:** **NULL means "inherit from the assigned plan."** The resolution rule is `effective = unit.value ?? plan.value ?? null`. A unit with no plan and a NULL column simply has no value, which is exactly today's behaviour. `0` is a real value, not an absence — a 0-bedroom studio override is expressible.
- **D-19:** **Inheritance resolves at read time, so plan edits propagate live.** Editing a plan's square footage instantly moves every unit that has not been individually overridden. Assignment must therefore **never copy** plan values into unit columns — a unit column is written only when the user explicitly types an override.
- **D-20:** The resolver is a **pure client-side function** in `apps/landlord-web/modules/units/lib/`, and `units.list` / `units.get` **stay unjoined**, consistent with the Phase 3 decision that the landlord UI builds its own lookup maps. Nothing server-side consumes effective bed/bath/sqft values in this phase. When server-side rent math arrives it gets promoted into `apps/server/src/domain/` — one function, one move, no duplicated logic in the meantime.

### Migration

- **D-21:** Generated with `drizzle-kit generate`, then **hand-appended** with the two audit triggers, because Drizzle does not emit them:
  ```sql
  CREATE TRIGGER floor_plans_audit AFTER INSERT OR UPDATE OR DELETE ON floor_plans
    FOR EACH ROW EXECUTE FUNCTION audit_log_trigger_fn();
  CREATE TRIGGER floor_plan_images_audit AFTER INSERT OR UPDATE OR DELETE ON floor_plan_images
    FOR EACH ROW EXECUTE FUNCTION audit_log_trigger_fn();
  ```
  The generated SQL must be **read before applying** to confirm both `ENABLE ROW LEVEL SECURITY` statements, both `organization_isolation` policies, the unique constraint, and the three `ALTER TABLE units ADD COLUMN` statements are present. Omitting an audit trigger is silent (Phase 3 Pitfall 6).
- **D-22:** `meta/_journal.json` is updated by the generator; the migration lands as `0017_*`. No data backfill is required — every new column is nullable or defaulted, and no existing row needs touching.

### API

- **D-23:** New module `apps/server/src/modules/floor-plans/` (`router.ts` / `service.ts` / `schemas.ts`), registered as `floorPlans` in `appRouter`. Schemas are exported for frontend reuse via a **new `"./schemas/floor-plans"` entry in `apps/server/package.json` exports** — without it the import resolves under the tsconfig path alias but fails at runtime.
- **D-24:** The gallery is a **nested sub-router** `floorPlans.gallery.{list,add,reorder,remove}`, structurally identical to `properties.gallery`. Reads use `protectedProcedure`; every mutation uses `permissionProcedure('write')`. Every procedure body runs inside `withOrganization(organizationId, userId, ...)`.
- **D-25:** Presigning lives in the **`uploads` module** as `uploads.presignFloorPlanImage({ floorPlanId, contentType, byteLength, filename? })`, alongside `presignPropertyImage` rather than in the new module. It validates the plan exists in-org, loads its `propertyId` to build the key (D-16), and rejects at 25 images.
- **D-26:** `floorPlans.list({ propertyId })` returns each plan plus a **`unitCount`** (grouped count query — the same approach `properties.service.listProperties` uses for its card footer) and a **presigned cover URL** (`sortOrder` 0, if any). Presigning is a local signature computation, not a network round trip, so one per plan is cheap.
- **D-26a:** `floorPlans.list` takes **`includeArchived?: boolean` (default `false`)** and every row carries its `archivedAt`. This is load-bearing, not a convenience: D-11 keeps archived plans supplying inherited values to already-assigned units, and the unit form and units table build their resolution lookup map from this list. If the list silently dropped archived plans, every unit assigned to one would render blank values — the exact data loss D-11 exists to prevent. **The unit form and units table request `includeArchived: true`** to build a complete map; the **assignment picker filters to non-archived** for its options.
- **D-27:** `units.create` and `units.update` accept optional `floorPlanId`, `bedrooms`, `bathrooms`. The service **validates that the referenced plan belongs to the unit's property** and rejects cross-property assignment with `BAD_REQUEST`. **Verify during planning** whether `updateUnitInputSchema` permits changing `propertyId`; if it does, a property change must also clear or re-validate `floorPlanId`, or a unit ends up inheriting from another property's plan.
- **D-28:** **No `PLAN_RESOURCES` change and no `me.get` quota field.** Floor plans are uncapped, so `plan_resource` enum, `plan_limits` seed rows, and the quota block are all untouched.

### UI — the `WizardDialog` primitive

- **D-29:** New file **`packages/ui/src/wizard-dialog.tsx`**, which **imports and composes** `Dialog`, `DialogPortal`, `DialogOverlay`, `DialogTitle` and `DialogDescription` from `dialog.tsx`. **`dialog.tsx` itself has a zero-byte diff** — this is an acceptance criterion, not an aspiration. Rejected alternative: a `variant` prop threaded through all seven existing dialog slots. A wizard needs *behaviour* (active step, advance gating, navigation), not just rotated layout, so a variant prop would solve half the problem while spreading branching across every consumer of the simple case.
- **D-30:** Exports: `WizardDialog` (root + step context), `WizardDialogContainer`, `WizardDialogSidebar`, `WizardDialogTitle`, `WizardDialogDescription`, `WizardDialogSteps`, `WizardDialogBody`, `WizardDialogFooter`, and the `useWizardDialog()` hook returning `{ steps, step, stepIndex, isFirst, isLast, next, back, goTo }`. Barrel-exported from `packages/ui/src/index.ts`.
- **D-31:** Layout: the container is a **`flex-row` shell at `sm:max-w-4xl`** (roughly double the current `sm:max-w-md`) capped at `max-h-[85vh]`, reusing `DialogContainer`'s exact rounding, border, shadow, and fade/zoom animation classes plus the same absolute top-right ghost close button. The sidebar is a fixed **`w-64 shrink-0`** column with `border-r` and the `bg-secondary` treatment `DialogHeader` uses today, so the wizard reads as the same design language rotated 90°. The body scrolls internally while the sidebar stays fixed; the footer sits at the bottom of the right column with the `bg-secondary` + `border-t` treatment of `DialogFooter`.
- **D-32:** **Responsive:** below the `sm` breakpoint the sidebar collapses to a top bar carrying the title and a compact `Step 2 of 3 · Gallery` line. The full vertical stepper is not rendered on mobile.
- **D-33:** Step state is **uncontrolled by default** (internal state seeded to `steps[0]`) with optional controlled `step` / `onStepChange`. It **resets to the first step whenever the dialog closes**, so reopening never lands mid-flow.
- **D-34:** A **`mode: "linear" | "free"`** prop drives navigation. `"linear"` (creation) requires steps in order and lets the stepper jump only to already-visited steps; `"free"` (editing) makes every step directly clickable. Advancement is gated by a **`canAdvance`** prop the consumer wires to form validity — `next()` no-ops when false and the stepper disables forward targets.
- **D-35:** **All step panels stay mounted**, with inactive ones hidden via the `hidden` attribute. This is what allows a **single `@tanstack/react-form` instance to span the whole wizard**: stepping back and forth never unmounts fields or resets state, and the review step reads live values from the same form. Conditional rendering would reintroduce exactly that bug.
- **D-36:** **No new dependency.** The stepper is composed from `PlatformIcon` and Tailwind. **Verify the completed-step check icon key** against the `PlatformIcon` map (Solar Linear) during planning rather than assuming a name.

### UI — floor plans feature

- **D-37:** Floor plans live **inside `modules/properties/`, not in a module of their own.** Modules are reserved for page-owning top-level domains; floor plans exist entirely within property settings. Layout:
  ```
  modules/properties/components/floor-plans/
    floor-plans-section.tsx
    floor-plan-card.tsx
    archive-floor-plan-dialog.tsx
    wizard/{floor-plan-wizard,details-step,gallery-step,review-step}.tsx
  modules/properties/lib/floor-plan-display.ts
  ```
- **D-38:** The surface is the **existing "Floor plans" `SettingsSection`** in `templates/settings/property-settings-units-template.tsx` — its placeholder `EmptyState` is replaced by `<FloorPlansSection propertyId />` (a card grid, an "Add floor plan" header action, and an empty state when there are none). **No new route, no new template file.**
- **D-39:** The card shows the cover thumbnail, the plan name, a formatted spec line (`2 bd · 1.75 ba · 1,100 sq ft`), the assigned unit count, and an edit/archive menu. The formatting helper — including "Studio" for 0 bedrooms, quarter-bath rendering, and omitting absent square footage — lives in `lib/floor-plan-display.ts` as a pure function.
- **D-40:** Wizard steps are **Details → Gallery → Review**. Details: name, bedrooms select, bathrooms select, optional default square footage with a "units can override this" hint. **The selects offer 0–10 while the Zod schemas accept 0–20 (D-07, D-08) — this asymmetry is deliberate:** the dropdowns cover every realistic residential layout without becoming unusable lists, and the wider schema range leaves headroom for a future numeric input without a migration. Do not "fix" one to match the other. Gallery: the staged uploader, 25 max, drag-reorder, first-is-cover, freely skippable (`canAdvance` stays true). Review: cover plus thumbnail strip, the spec line, image count, owning property, and an **Edit affordance per block that jumps back to that step**.
- **D-41:** **Images are staged locally and uploaded on Confirm**, reusing the proven `staged-gallery` pattern. The presign endpoint needs a `floorPlanId` that does not exist until create, and staging means an abandoned wizard leaves **zero orphaned rows and zero orphaned S3 objects**. Confirm runs `floorPlans.create`, then persists staged images, then invalidates.
- **D-41a:** A consequence worth stating: **while images are staged, the server has not seen them**, so the 25 cap and the MIME/size rules are enforced during staging by the client-side `acceptImageFiles` helper alone (`remainingSlots` = 25 − staged count). D-14's server-side checks still fire per image at persist time, so the cap cannot actually be exceeded — but the *user-facing* refusal message in the wizard comes from the client helper, and it must be wired or the cap appears absent until Confirm.
- **D-42:** **Editing reuses the same wizard** opened with values pre-loaded, `mode="free"`, and **no review step** — Details and Gallery only, with the footer becoming a `SubmitButton` matching the `general-form.tsx` status/steps pattern. Images stay **staged in edit mode too** and persist on Save, so creation and editing share one gallery code path rather than diverging into staged-vs-live.
- **D-43:** The only pre-existing code touched: **`persistStagedGallery` loses its explicit `propertyId` parameter**, since its upload callbacks are already injected and can close over whichever owner id they need. The staged-gallery files stay where they are — floor plans live in the same module (D-37), so no relocation is needed.
- **D-44:** Archive confirmation uses the **standard, unmodified `Dialog`**. The wizard variant is for multi-step flows; a confirm prompt is not one.
- **D-45:** **Unit form sheet** gains a floor plan select (that property's non-archived plans plus an explicit "None") and Bedrooms / Bathrooms fields beside the existing Square footage. When a plan is selected and a field is left empty, **the plan's value renders as the input's placeholder** with an "Inherited from {plan name}" hint. **Clearing a field is how the user returns to inheriting** — this must be reachable, or D-19's live propagation becomes a one-way door.
- **D-46:** **Units table** gains Beds, Baths and Floor plan columns, with inherited values rendered muted so an override is visually distinguishable from an inherited value.
- **D-47:** Invalidation per the `CLAUDE.md` checklist. Plan create/update/archive → `floorPlans.list`, `floorPlans.get`, `properties.get`. Unit mutations keep their existing set (`units.list`, `units.get`, `properties.get`, `me.get`). **`me.get` is not needed for plan mutations** — floor plans carry no quota (D-28).

### Testing & verification

- **D-48:** New `apps/server/src/__tests__/floor-plans.test.ts` following the `properties.test.ts` shape (`setupOwner`, direct tRPC caller, no HTTP): plan CRUD, per-property name uniqueness, **cross-property assignment rejection**, archive leaving assigned units intact, cross-organization RLS isolation, and the 25-image cap on the new gallery (mirroring `gallery.test.ts`). Inheritance resolution is client-side (D-20) and therefore not server-tested.
- **D-49:** **There is no component test infrastructure** in the monorepo (03.1 D-46). The wizard's interactive behaviour is **manually verified**. If Phase 3.1 landed its `packages/ui` node-environment vitest project, the pure helpers — `floor-plan-display` formatting and any step-resolution logic — are unit tested there; standing up jsdom is out of scope.
- **D-50:** **Phase 3.1 D-49 carries forward verbatim: every shell command in every plan must run in Windows PowerShell 5.1.** No `&&` chaining, no `grep`, no `find`, no `2>/dev/null`; use `;`, `rg` (with `-F` for literal source text), `Get-ChildItem -Recurse`, and `master` as the git base branch. An acceptance criterion that cannot execute is not a criterion.

### Reusable Assets

- **The property gallery is a complete working template** for the floor plan gallery: `property_images` table shape, the presign → browser `PUT` → `gallery.add` three-step flow, the double-enforced 25 cap, index-based reorder, and S3-delete-then-row-delete. The floor plan gallery is a structural copy, not a new design.
- **`persistStagedGallery` already takes injected `presign` / `add` / `remove` / `reorder` callbacks**, so retargeting it at floor plans is a signature simplification (D-43), not a rewrite.
- **`StagedGalleryField` already models `{ kind: "existing" }` items**, which is precisely what edit mode needs (D-42).
- **`unitStatuses` supplies both missing precedents at once**: a nullable FK from `units` with `onDelete: 'set null'`, and an org-scoped unique-name constraint.
- **`DialogContainer` already carries** the rounding, border, shadow, animation and close-button treatment the wizard container needs — the wizard reuses the class list rather than inventing one.
- **`properties.service.listProperties` already does a grouped `unitCount`** query, which is the exact shape `floorPlans.list` needs (D-26).

### Established Patterns

- Pages are thin Server Component shells delegating to client templates in `modules/{domain}/templates/`; modules organize as `components/` grouped by feature, plus `templates/`, `lib/`, `providers/`.
- Naming is `{feature}-{type}.tsx` (`unit-form-sheet.tsx`, `archive-unit-dialog.tsx`).
- Forms use `@tanstack/react-form` with **individual fields validated against `someInputSchema.shape.field`** and the **whole payload parsed on submit**; errors surface through `fieldError(meta)` into the input's `error` prop.
- Server modules are `router.ts` (procedures + `withOrganization` + permission gate) / `service.ts` (Drizzle, accepts `OrganizationTx`) / `schemas.ts` (Zod, the API contract).
- Closed option sets the app owns become real Postgres enums built from the same `as const` array the Zod validator uses. **Bedrooms and bathrooms are deliberately not enums** (D-08) — they are open numeric ranges.

- **No dialog in the codebase is multi-step**, and every existing `DialogContainer` call site is `sm:max-w-sm`/`md`/`lg`. The wide two-column form factor is unprecedented here.

<specifics>
## Specific Ideas

- The wizard primitive's success test is **reuse cost**: a second wizard (a future lease or onboarding flow) should cost a `steps` array, panels, and a footer — no new layout code, no forked container. If the floor plan wizard has to reach into the primitive's internals, the boundary is wrong.
- **`dialog.tsx` must have a zero-byte diff at the end of this phase.** The existing dialogs are considered correct and finished; the wizard is additive.
- The left sidebar should feel like the current `DialogHeader` rotated, not like a new component — same `bg-secondary`, same title/description typography, same border treatment.
- **Never copy plan values into unit columns.** The single most likely way to build this wrong is to "prefill" the unit's fields on assignment, which silently converts every unit into an override and makes plan edits no-ops. Inheritance is a read-time fallback; a unit column is written only when the user types in it.
- A landlord must be able to **un-override** — clearing a field returns it to inheriting (D-45).
- Because bathrooms are `numeric`, watch for the **string-vs-number boundary** (D-07). A `"1.75"` leaking into the UI breaks the select's value match and the formatter silently.

### Suggested wave shape (planner may revise)

1. **Schema + migration** — both tables, three `units` columns, RLS policies, audit triggers, journal. Blocking; nothing else starts until the migration applies cleanly.
2. **API** *(parallel-ish)* — `floorPlans` module + nested gallery + `uploads.presignFloorPlanImage`; `units` input widening + cross-property validation; `floor-plans.test.ts`.
3. **`WizardDialog` primitive** — independent of everything above; can run alongside wave 2. Ends with a throwaway harness or the real wizard proving the layout, plus barrel export.
4. **Floor plans UI** — `FloorPlansSection`, card, wizard steps, staged gallery retarget, archive dialog, overlay registration. Depends on 2 and 3.
5. **Unit assignment** — plan select, beds/baths fields with inherited placeholders, resolver, table columns. Depends on 2 and 4 (shares the unit form).

### Verification (must be demonstrated, not assumed)

- Create a plan through all three steps with images; confirm the review step shows what was entered and the created plan appears with its cover thumbnail.
- **Abandon the wizard mid-gallery** and confirm no `floor_plans` row and no S3 object were created.
- Assign a plan to a unit, leave all three fields empty, then **edit the plan's square footage and watch the unit's displayed value change**.
- Override one unit's square footage, re-edit the plan, and confirm **that unit alone** keeps its own number.
- Clear an overridden field and confirm the unit returns to inheriting.
- Attempt to assign a plan from a different property (via a crafted tRPC call) and confirm rejection.
