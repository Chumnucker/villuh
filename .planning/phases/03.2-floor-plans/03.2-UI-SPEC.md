# Phase 3.2 — UI Design Contract

> Visual and interaction contract for Phase 3.2: Floor Plans.
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.

**Scope note:** Two things ship: the reusable **`WizardDialog` primitive** in `@villuh/ui`, and the **floor plans feature** inside property settings. There is **no new route**, **no new template file**, and **no resident-web surface**. Every surface below is an in-page region or an overlay, not a page — the "Screen N" numbering is kept for continuity with `03-UI-SPEC.md`.

**Inherited wholesale from Phase 3:** design system, spacing scale, typography, color roles, interaction states. Only the deltas are restated here.

**Hard constraint carried into every section:** `packages/ui/src/dialog.tsx` ends this phase with a **zero-byte diff** (D-29). Nothing in this contract asks for a change to it. The four pre-existing dialogs (tags, archive property, archive unit, plan limit) must render identically before and after.

## Spacing Scale

Standard 8-point scale, inherited from Phase 2/3 unchanged. All values are multiples of 4.

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px (`gap-1`) | Icon-to-label gap in stepper badge; card text block internal gap |
| sm | 8px (`gap-2`, `p-2`) | Footer button gap; review thumbnail strip gap; stepper connector clearance |
| md | 16px (`px-4`, `gap-4`) | Sidebar padding (`px-4 py-4`, matching `DialogHeader`); card content padding; wizard field grid gap; floor plan card grid gap |
| lg | 24px (`px-6`, `py-6`) | Wizard body padding; stepper row vertical rhythm |
| xl | 32px (`gap-8`) | Not used this phase |
| 2xl | 48px (`py-12`, `pt-12`) | Empty-state vertical breathing room; wizard body top padding on `sm:` and up |
| 3xl | 64px | Not used this phase |

Exceptions (each justified, none arbitrary):

- **Wizard sidebar width: `w-64` (256px)** — mandated by D-31. 256 is a multiple of 4.
- **Wizard container: `sm:max-w-4xl` (896px), `max-h-[85vh]`** — mandated by D-31. `85vh` is a viewport unit, not a spacing token; it does not belong on the 4px grid.
- **Wizard body minimum height: `min-h-80` (320px)** — see "Height jump" under the primitive contract. Not decorative; it stops the dialog resizing between steps.
- **Stepper badge: `size-6` (24px), inner dot `size-2` (8px), connector `h-6 w-px`** — the connector is 1px by definition of a hairline rule; every other value is on-scale.
- **Icon-only buttons: `size-8` (`size="icon-sm"`)** — the existing `Button` size token used by every overflow menu in the app. Below the 40px ideal, but it is the established value and changing it is out of scope.
- **Floor plan card cover: `aspect-[3/2]`** — a ratio, not a length. Chosen over `aspect-square` because a floor plan drawing is wider than tall, and over `aspect-video` because 16:9 crops plan drawings too aggressively.
- **Review thumbnail strip: `size-16` (64px)** — on-scale.

Custom tokens already in `globals.css` and unchanged: `--spacing-navbar: 3.75rem`, `--page-padding: 1rem`, `--content-padding: 1.5rem`.

## Screens and Interaction Contracts

### Screen 1: The `WizardDialog` primitive — `packages/ui/src/wizard-dialog.tsx`

This is the highest-value part of the phase. It is a **general-purpose `@villuh/ui` primitive** that future lease and onboarding flows will consume. Its success test (CONTEXT `<specifics>`): a second wizard costs a `steps` array, panels, and a footer — no new layout code, no forked container. If a consumer has to reach into the primitive's internals, the boundary is wrong.

#### 1.1 Container geometry

Composes `DialogContainer` with className overrides. `cn()` is `twMerge(clsx(...))`, so conflicting classes resolve last-wins per breakpoint group:

```
max-h-[85vh] sm:max-w-4xl flex-col sm:flex-row
```

| Inherited unchanged from `DialogContainer` | Why it matters |
|--------------------------------------------|----------------|
| `rounded-4xl border bg-popover shadow-xl` | The wizard reads as the same object family as every other dialog |
| `overflow-hidden` | Clips the sidebar's `bg-secondary` to the container's corner radius |
| `fixed top-1/2 left-1/2 -translate-x-1/2 -translate-y-1/2 z-50` | Centering |
| `max-w-[calc(100%-2rem)]` | Survives the override (different breakpoint group from `sm:max-w-4xl`) — below 640px the container is viewport-width minus 32px, never 896px |
| `data-open:animate-in data-open:fade-in-0 data-open:zoom-in-95 data-closed:animate-out data-closed:fade-out-0 data-closed:zoom-out-95 duration-100` | Identical open/close motion to every existing dialog |
| The absolute top-right ghost close button | `<Button variant="ghost" size="icon-sm" className="absolute top-2 right-2">` + `IconCrossLarge` at 16px + `<span className="sr-only">Close</span>` |
| `text-sm text-popover-foreground` | Body typography baseline |

| Overridden | From → To | Why |
|------------|-----------|-----|
| `flex-col` | → `flex-col sm:flex-row` | The two-column shell above `sm`; the mobile stack below it (D-32) |
| `sm:max-w-md` | → `sm:max-w-4xl` | 448px → 896px (D-31) |
| — | + `max-h-[85vh]` | Caps height so the body scrolls rather than the page (D-31) |

**Close-button collision — resolved, not ignored.** The close button is positioned against the *container*, so above `sm` it floats over the top-right of the **body** column, and below `sm` it floats over the top-right of the **sidebar-as-top-bar**. Two paddings clear it:

- `WizardDialogBody`: `px-6 pt-6 pb-6 sm:pt-12` — 48px top padding above `sm` clears the 34px-tall close button plus breathing room. Without this, the Gallery step's right-aligned "Add photos" button sits underneath it.
- `WizardDialogSidebar`: `pr-12 sm:pr-4` — below `sm` the compact step line must not run under the close button.

**Tab order consequence:** `DialogContainer` renders `{children}` and *then* the close button, so Close is the **last** element in DOM order — after the footer. This is inherited behavior shared with every existing dialog and is left as-is.

flex shrink-0 flex-col gap-2.5 border-b bg-secondary px-4 py-4 pr-12
sm:w-64 sm:border-r sm:border-b-0 sm:pr-4

| Piece | Treatment |
|-------|-----------|

#### 1.3 The vertical stepper — `WizardDialogSteps`

**Nothing like this exists in the codebase.** `packages/ui/src/progress.tsx` is a bare Radix progress bar and is not reused. Built from scratch with `PlatformIcon` + Tailwind (D-36).

**Structure and semantics:**

```
<nav aria-label="Wizard steps">
  <ol className="flex flex-col">
    <li className="relative pb-6 last:pb-0">
      {/* connector — omitted on the last item */}
      <span aria-hidden className="absolute left-3 top-6 h-6 w-px -translate-x-1/2 {connector}" />
      <button type="button" aria-current={isCurrent ? "step" : undefined} disabled={!reachable}>
        <span className="{badge}">{marker}</span>
        <span className="{label}">{step.label}</span>
        <span className="sr-only">{stateWord}</span>
      </button>
    </li>
  </ol>
</nav>
```

- It **is** a `<nav>` containing an ordered list. Steps **are** `<button type="button">` — they navigate within a dialog, they are not links and there is no route.
- `aria-current="step"` on the current step only.
- Unreachable steps carry the real `disabled` attribute — removed from the tab order, not merely dimmed.
- The checkmark is `aria-hidden`; an `sr-only` state word (`Completed` / `Current step` / `Not started`) carries the meaning. **Color is never the only signal.**
- Connector is `aria-hidden` — decorative.

**Button row:** `flex w-full items-center gap-3 rounded-lg text-left focus-visible:ring-1 focus-visible:ring-ring/35 focus-visible:ring-offset-1 focus-visible:ring-offset-background disabled:pointer-events-none disabled:opacity-50` — the focus ring is copied from `buttonVariants` so it matches every other focusable thing in the app.

**Every visual state, exhaustively:**

| State | Condition | Badge (`size-6 rounded-full flex items-center justify-center`) | Marker | Label |
|-------|-----------|--------------------------------------------------------------|--------|-------|
| **Completed** | `visited.has(id) && id !== activeId` | `border border-primary bg-primary text-primary-foreground` | `<PlatformIcon icon="IconCheckmark1" size={12} strokeWidth={3} />` | `text-sm text-foreground` |
| **Current** | `id === activeId` | `border-2 border-primary bg-background` | `<span className="size-2 rounded-full bg-primary" />` | `text-sm font-medium text-foreground` |
| **Visited-but-not-current** | `visited.has(id) && id !== activeId` — **same as Completed** | as Completed | as Completed | as Completed |
| **Upcoming, reachable** (`mode="free"`, or the immediate next step when `canAdvance`) | `!visited.has(id) && reachable` | `border border-border bg-background` | `<span className="size-2 rounded-full bg-muted-foreground/40" />` | `text-sm text-muted-foreground` |
| **Upcoming, unreachable** (`mode="linear"`, not yet visited) | `!reachable` | as Upcoming-reachable, plus the row's `disabled:opacity-50` | as Upcoming-reachable | as Upcoming-reachable |
| **Disabled forward target** (`canAdvance === false`) | `!reachable` for the same reason | as Upcoming-unreachable — **identical rendering** | — | — |

Two deliberate collapses, stated so they are decisions rather than oversights:

1. **"Visited-but-not-current" and "completed" render identically.** Stepping back from Gallery to Details leaves Gallery visited-and-ahead. It has data and is one click away, so it earns the checkmark. Distinguishing "done and behind you" from "done and ahead of you" would be a distinction without a user-facing meaning, and D-35 keeps its panel mounted either way.
2. **"Disabled forward target" and "upcoming unreachable" render identically.** When `canAdvance` is false the next step is simply not reachable yet; a third greyed variant would imply a fourth state the user cannot act on differently. The *reason* is communicated where the user can act on it — inline field errors in the body, and the disabled Next button in the footer. Do not add a tooltip on a `disabled` button; `disabled:pointer-events-none` means it can never fire.

**Connector line:** `absolute left-3 top-6 h-6 w-px -translate-x-1/2`. `left-3` (12px) is the horizontal center of the `size-6` badge; `top-6` (24px) is its bottom edge; `h-6` (24px) exactly spans the `pb-6` gap to the next badge. Color: **`bg-primary` when the step above it is completed, `bg-border` otherwise** — so the primary-colored trail visually measures progress down the column. Omitted entirely on the last item (`last:pb-0` also removes the gap it would occupy).

**Numeral-vs-checkmark:** there is no numeral. Completed steps show `IconCheckmark1`; every other state shows a dot. Ordinal position is already carried by the vertical ordering and the `<ol>` semantics, and D-32's mobile bar carries the explicit `Step 2 of 3` count. Adding numerals inside a 24px badge would require a fourth type size below `text-sm`, which the typography contract forbids.

#### 1.4 Body — `WizardDialogBody` + `WizardDialogPanel`

```
WizardDialogBody:  min-h-0 min-h-80 flex-1 overflow-y-auto px-6 pt-6 pb-6 sm:pt-12
WizardDialogPanel: (root div, hidden={step !== active}, tabIndex={-1})
```

- `min-h-0` is **required**: without it a `flex-1` child in a flex row/column refuses to shrink below its content height and `overflow-y-auto` never scrolls. The sidebar stays fixed because it is `shrink-0`; only this column scrolls.
- **All panels stay mounted; inactive ones are hidden via the `hidden` attribute** (D-35). This is what lets one `@tanstack/react-form` instance span the whole wizard — stepping back and forth never unmounts a field, and the Review step reads live values from the same form.

**Three visual consequences of `hidden`, all binding:**

1. **The panel root must not carry a `display` utility.** `hidden` is `display: none`, and any Tailwind `flex` / `grid` / `block` class on the same element overrides it — the panel would render on top of the active one. Put layout classes on a **child** wrapper, never on the panel root.
2. **Height jumps between steps.** `display: none` removes hidden panels from layout entirely, so the dialog's height is driven by the active panel alone: Details (four fields) is much shorter than Gallery (a 25-tile grid). `min-h-80` (320px) on the body sets a floor so short steps do not collapse into a visibly smaller box. Above that floor the container still grows, capped by `max-h-[85vh]`, which is correct — a tall Gallery step should use the space.
3. **Hidden fields are out of the tab order and out of the accessibility tree.** This is the desired behavior: focus can never land in an invisible step's inputs. It also means a validation error on a hidden step is announced to nobody — the consumer must surface cross-step validity through the footer's disabled Next button and through the stepper, which this contract already does.

**Focus on step change:** after the active step changes, focus moves to the newly-shown panel root (`tabIndex={-1}` + `.focus()`), **skipped on the initial mount** so it does not fight Radix's own initial autofocus. Rationale: a keyboard user who presses Next lands at the top of the new panel and tabs forward into its first field, rather than being dumped back at the start of the sidebar.

**Keyboard contract:**

| Key | Behavior |
|-----|----------|
| `Tab` | Sidebar stepper buttons (reachable ones only) → body fields of the active panel → footer buttons → close button |
| `Shift+Tab` | Reverse; focus is trapped inside the dialog by Radix |
| `Esc` | Closes the dialog (Radix default). Step state resets to `steps[0]` on close (D-33), so reopening never lands mid-flow |
| `Enter` in a text field | **Must not** submit. The wizard's `<form onSubmit>` calls `next()` when not on the last step and `preventDefault()`s otherwise; the footer's Next is `type="button"`. Without this, Enter in the Name field creates the plan from the Details step |
| `Space` / `Enter` on a stepper button | `goTo(id)` — no-op for disabled steps |

#### 1.5 Footer — `WizardDialogFooter`

Bottom of the right column. Class string is **byte-identical to `DialogFooter`** so the two read as the same component:

```
flex flex-col-reverse gap-2 bg-secondary border-t px-4 py-2.5 sm:flex-row sm:justify-end
```

Below `sm`, `flex-col-reverse` stacks the primary action on top — inherited behavior, correct on a phone.

| Mode | Not last step | Last step |
|------|---------------|-----------|
| Create (`linear`) | **Back** (`variant="outline"`, `IconChevronLeft` `data-icon="inline-start"`) — hidden on the first step · **Next** (default, `IconChevronRight` `data-icon="inline-end"`, `disabled={!canAdvance}`) | **Back** · **Create floor plan** (`SubmitButton`, steps `["Create floor plan", "Creating…", "Created", "Error"]`) |
| Edit (`free`) | **Discard changes** (`variant="outline"`, rendered only when the form is dirty) · **Save changes** (`SubmitButton`, steps `["Save changes", "Saving…", "Saved", "Error"]`) | same — edit mode has no last-step branch (D-42: no Review step) |

`SubmitButton`'s `status` comes from `submitStatus(isSubmitting, mutation.isPending, isError)` in `property-form-shared.ts` — the same helper `general-form.tsx` uses. This is D-42's "matching `general-form.tsx`'s status/steps pattern", literally.

#### 1.6 Responsive — below `sm` (D-32)

The container becomes `flex-col`; the sidebar becomes a top bar. **The full vertical stepper is not rendered.**

Collapsed bar, precisely:

| Property | Value |
|----------|-------|
| Element | The same `WizardDialogSidebar` div, restyled by its own breakpoint classes — not a separate component |
| Layout | `flex flex-col gap-2.5` (as desktop), full width, `border-b`, `bg-secondary` |
| Padding | `px-4 py-4 pr-12` — the `pr-12` clears the close button |
| Line 1 | `WizardDialogTitle` — `font-heading text-base leading-none font-medium`, e.g. **New floor plan** |
| Line 2 | The compact step line: `text-sm text-muted-foreground`, format **`Step 2 of 3 · Gallery`** — literal ` · ` separator (space, U+00B7, space), matching the spec-line separator used everywhere else in this phase |
| Not rendered | `WizardDialogDescription` (`hidden sm:block`) — two lines of prose above a form on a 375px screen pushes the first field below the fold |
| Not rendered | The `<nav>` stepper (`hidden sm:block`) |
| Navigation | Back / Next in the footer only. Direct step jumping is unavailable on mobile — acceptable for a 3-step flow, and `mode="free"` edit is 2 steps |

The compact line is derived from the same context (`stepIndex`, `steps.length`, `step.label`), so it can never disagree with the stepper.

#### 4.1 Details step

Panel child wrapper: `grid gap-4 sm:grid-cols-2`. `canAdvance` = the three required fields are valid.

| # | Field | Control | Span | Notes |
|---|-------|---------|------|-------|
| 1 | **Name** | `Input`, required | `sm:col-span-2` | Placeholder `2 bed / 2 bath`. Validated per-field against `createFloorPlanInputSchema.shape.name` on change and blur, per the house form pattern |

The selects offering 0–10 while the Zod schemas accept 0–20 is **deliberate and locked** (D-40). Do not "fix" either to match the other.

Bathrooms uses 0.25 increments, not 0.5: the entire point of `numeric(4,2)` + `multipleOf(0.25)` (D-07) is quarter baths, and a half-step select would make `1.75` unreachable from the UI while the schema advertises it. 41 options in a scrolling `Select` is acceptable — the primitive already scrolls.

**Duplicate name (D-09):** a per-property unique-constraint violation surfaces as a **field-level error under the Name input** via `FieldError`, not a toast. It arrives from the server as a mutation error, so the wizard maps it onto the name field and jumps back to the Details step if the user is not already there. Copy in the Copywriting Contract.

#### 7.1 Floor plan select

- `Select` with an explicit `<SelectItem value={NO_FLOOR_PLAN}>None</SelectItem>` first, then that property's **non-archived** plans alphabetically.
- Item label: `{plan.name}` followed by `<span className="text-muted-foreground"> · {spec}</span>` — the spec is what tells a landlord whether they picked the right plan.
- **Archived-plan edge case, mandatory:** if the unit is already assigned to an archived plan, that plan is **not** in the option list and the trigger would render blank. The currently-assigned plan is therefore always appended to the options, labeled `{name} (archived)`. D-26a's `includeArchived: true` fetch exists precisely so this is possible.
- Disabled when no property is selected yet (global `/units` create), with `SelectValue placeholder="Select a property first"`.
- `FieldDescription` when a plan is selected: **Beds, baths, and square footage come from this plan unless you set them below.**

#### 7.2 Bedrooms / Bathrooms / Square footage — the inheritance triplet

All three are **number `Input`s**, not selects:

```
Bedrooms          <Input type="number" min={0} inputMode="numeric" />
Bathrooms         <Input type="number" min={0} step="0.25" inputMode="decimal" />
Square footage    <Input type="number" min={0} inputMode="numeric" />   (unchanged)
```

**Why inputs here when the wizard uses selects:** D-45 says the plan's value renders as "the input's **placeholder**", and clearing a field is how a user returns to inheriting. An empty text input with a muted placeholder expresses "unset, showing the inherited value" natively, and deleting the text is the most obvious clear gesture there is. A `Select` would need an invented `__inherit__` sentinel option to express the same thing. The wizard's selects (D-40) are a different problem — there the value is required, so there is no empty state to express.

**Placeholder = the inherited value.** When a plan is assigned and the field is empty:

```
placeholder={String(plan.bedrooms)}     // renders muted via Input's own
                                         // placeholder:text-muted-foreground
```

`Input`'s base classes already include `placeholder:text-muted-foreground placeholder:font-normal`, so the inherited number is visually distinct from a typed override with no extra styling. When no plan is assigned, the placeholder is empty and the field simply has no value.

**The hint line under each field** — this is what makes un-overriding discoverable, and it is required (D-45, CONTEXT `<specifics>`):

| Situation | `FieldDescription` content |
|-----------|----------------------------|
| Plan assigned, field empty | `Inherited from {plan name}` |
| Plan assigned, field has a value | `Overrides {plan name}` + an inline **Clear** button |
| No plan assigned | no hint |

The **Clear** affordance is a real control, not just copy: `<button type="button" className="text-sm text-muted-foreground underline underline-offset-3 hover:text-foreground">Clear</button>` — the link treatment `DialogDescription` already defines (`underline underline-offset-3 hover:text-foreground`). It sets the field to empty, which restores inheritance. Rendered inline at the end of the hint row.

**`0` is a real value, not an absence** (D-18). A unit with `bedrooms = 0` is an explicit studio override and must render `0` in the input with the "Overrides" hint — not fall through to the plan's value. This is the `??` vs `||` trap; a `||` here silently deletes every studio override.

**Never copy plan values into the unit's fields on assignment** (D-19, CONTEXT `<specifics>`). Selecting a plan changes only the placeholder and the hint. If assignment prefilled the inputs, every unit would silently become an override and plan edits would become no-ops. This is the single most likely way to build this screen wrong.

### Screen 8: Units table columns (D-46)

Three columns added to `units-columns.tsx`, and one existing column gains inheritance behavior. Final order:

`Unit · Property · Status · Base rent · Beds · Baths · Sq ft · Floor plan · Actions`

Beds / Baths / Sq ft sit together because they are the same family of number; Floor plan follows them because it explains them. Actions stays anchored last (`meta: { enableMoving: false }`).

**The muted treatment — exact, and the whole point of D-46:**

| Cell state | Rendering |
|------------|-----------|
| **Override** (unit's own column is non-null) | `<span className="text-foreground">{value}</span>` — the table's default cell color, full contrast |
| **Inherited** (unit column null, plan supplies it) | `<span className="text-muted-foreground" title="Inherited from {plan name}">{value}<span className="sr-only"> (inherited)</span></span>` |
| **Neither** (no plan and no override) | `<span className="text-muted-foreground">—</span>` |

Reading side by side: a column of `oklch(0.552 0 0)` grey numbers with one `oklch(0.141 0 0)` near-black number — the override is the dark one. The contrast step between `--muted-foreground` and `--foreground` is large enough to read at a glance in both themes (dark mode: `0.705` vs `0.985`).

**Color is not the only signal.** The `sr-only` "(inherited)" suffix carries it for screen readers and the `title` gives a hover explanation naming the plan. Without these, the distinction would be invisible to a colorblind or non-sighted user, and "which of these did I set myself" is exactly the question the column exists to answer.

**Sq ft must adopt this too.** It currently renders `{row.original.squareFootage ?? "—"}`, which after this phase would show `—` for a unit that visibly inherits 1,100 sq ft from its plan. It renders the **resolved** value with the same three-state treatment.

**Floor plan column:** `text-muted-foreground` plan name; `—` when unassigned; `{name} (archived)` when the assigned plan is archived. Always muted — it is a reference, never an override.

**Sortability:** Beds, Baths, and Floor plan are **not sortable**. They display client-resolved values the server never computes (D-20), so a server sort would order by the raw nullable column and disagree with what is on screen. Do not widen `UNIT_SORT_KEYS`. The existing Sq ft sort behavior is flagged in Open Questions for the same reason.

**Resolution source:** both the table and the unit form build their lookup map from `floorPlans.list` with **`includeArchived: true`** (D-26a). If the map silently dropped archived plans, every unit assigned to one would render blank — the exact data loss D-11 exists to prevent.

## Blockers

**None.** Every locked decision in CONTEXT D-29 through D-47 is visually achievable as stated. The two that looked risky were checked against real source and resolved:

1. **D-29 + D-31 together** ("reuse `DialogContainer`'s exact rounding, border, shadow, animation and close button" while `dialog.tsx` has a zero-byte diff). `DialogContainer` renders its own `DialogPortal` + `DialogOverlay` internally and does not forward the raw Radix `Content`, so it cannot be extended structurally — but it accepts `className`, and `cn()` is `twMerge(clsx(...))`, which resolves conflicting classes last-wins **per breakpoint group**. `className="max-h-[85vh] sm:max-w-4xl flex-col sm:flex-row"` overrides `flex-col` and `sm:max-w-md` while inheriting everything else, including the close button. Satisfied literally, no file edit.

2. **D-31's close button vs. D-32's mobile top bar.** The button is positioned against the container, so it lands on the body above `sm` and on the top bar below it. Resolved with `sm:pt-12` on the body and `pr-12 sm:pr-4` on the sidebar. Without both, the Gallery step's "Add photos" button and the mobile compact step line render underneath it.

One item is **flagged, not blocking**: D-30's export list omits `WizardDialogPanel`, which D-35 requires. Listed in Open Questions.

## Open Questions

Five items where a defensible answer exists but the decision is not mine to lock. Each carries a recommendation; the orchestrator should relay them.

**1. `StagedGalleryField`'s empty-state copy inside the wizard.**
The component's empty state reads *"Drop in property photos — they upload when you save."* Rendered inside a floor-plan wizard, that says "property photos". D-43 names `persistStagedGallery` as the **only** pre-existing file touched, so fixing it means a second file.
**Recommendation:** add two optional props (`emptyTitle`, `emptyDescription`) defaulting to the current strings. This is strictly additive, leaves the property form byte-identical in behavior, and is a 4-line change. The alternative — accepting "property photos" in a floor-plan wizard — is a small but real copy defect on a brand-new surface. *If the answer is "accept it", the Copywriting Contract row must be changed back to the existing string so the checker does not flag a mismatch.*

**2. `WizardDialogPanel` is not in D-30's export list.**
D-30 enumerates nine exports plus the hook; `WizardDialogPanel` is not among them. But D-35 requires every step panel to stay mounted with `hidden` toggled, and the hidden-vs-active decision needs the step context. Leaving it unexported forces every consumer to call `useWizardDialog()` and hand-roll the `hidden` logic — which is exactly the "reaching into the primitive's internals" failure CONTEXT `<specifics>` names as the sign the boundary is wrong.
**Recommendation:** export it. It is an omission in the enumeration, not a decision against it.

**3. The Beds / Baths / Sq ft columns and server sorting.**
Beds, Baths and Floor plan are specified non-sortable because they render client-resolved values the server never computes (D-20). **Sq ft is different** — it is an existing, possibly server-sortable column that is now *also* inheritance-resolved. Sorting it would order by the stored override and disagree with what is displayed, for the same reason.
**Recommendation:** make Sq ft non-sortable too, for consistency and correctness. It is a small regression in capability that removes a confusing wrong answer. *Requires confirming whether `squareFootage` is currently in `UNIT_SORT_KEYS`.*

**4. Bathrooms select granularity in the wizard.**
Specified as 0–10 in 0.25 increments = **41 options**. That is a long scrolling list, but a 0.5-step select would make `1.75` unreachable from the UI while the schema (D-07) exists specifically to store it.
**Recommendation:** keep 41 options. The alternative that preserves quarter baths with a shorter list is a number input with `step="0.25"` — but D-40 explicitly says "bathrooms select", so changing the control type is a decision, not an implementation detail. *This is the one place where the locked wording and the shortest good UI are in mild tension.*

**5. "Studio" in the units table Beds column.**
The spec line renders `bedrooms === 0` as **Studio** everywhere (D-08). This contract makes one exception: the units table's Beds column shows the raw `0`, because a column mixing `Studio` / `2` / `3` breaks numeric scanning and loses right-alignment.
**Recommendation:** keep the exception. If the user prefers absolute consistency, the change is one line in the column cell — but the spec line and the table are different reading tasks.
