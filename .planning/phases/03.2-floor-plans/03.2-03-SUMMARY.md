# Phase 03.2 Plan 03: Units Floor-Plan Assignment API Summary

**`units.create`/`units.update` widened with optional `floorPlanId`/`bedrooms`/`bathrooms`; a `requireFloorPlanInProperty` guard rejects cross-property assignment with `BAD_REQUEST` on both paths; a unit's property is now immutable on update (D-27a) and `squareFootage` is gone from the server sort enum — with no plan values ever copied into unit columns.**

## Performance
- **Duration:** ~10 min
- **Tasks:** 2 completed
- **Files:** 2 modified

## Accomplishments
- `createUnitInputSchema` gains `floorPlanId: z.uuid().optional()`, `bedrooms: z.number().int().min(0).max(20).optional()`, `bathrooms: z.number().multipleOf(0.25).min(0).max(20).optional()` — widened without breaking existing callers (D-27).
- `updateUnitInputSchema` now `createUnitInputSchema.omit({ propertyId: true }).partial().extend({ unitId })` — `propertyId` cannot be sent on update at the type or runtime boundary (D-27a, T-03.2-09).
- `squareFootage` removed from `UNIT_SORT_KEYS` (leaving `['label','propertyName','status','baseRent']`) and from the coupled `UNIT_SORT_COLUMNS` map (D-46). The `squareFootage`/`squareFootageEmpty` numeric-filter fields on `listUnitsInputSchema` were left untouched — only the sort key was removed.
- New `requireFloorPlanInProperty(tx, orgId, floorPlanId, propertyId)` guard: queries `floor_plans` in-org and calls `badRequest('That floor plan belongs to a different property.')` when the plan is missing in-org or its `propertyId` differs (D-27, T-03.2-08).
- `createUnit` validates a supplied `floorPlanId` against `input.propertyId`, then writes the three new columns with `?? null` — never copying plan values (D-19).
- `updateUnit` captures `existing`, validates a supplied `floorPlanId` against the immutable `existing.propertyId`, and patches `bedrooms`/`bathrooms`/`floorPlanId` only when supplied (`?? null` clears back to inheriting per D-45; absent leaves the column alone per D-19). No effective/inherited value is ever computed or stored (D-20).
