# Phase 3.2: Floor Plans - Research

**Researched:** 2026-08-13
**Domain:** Postgres/Drizzle schema extension + tRPC module + S3 gallery replication + a new `@villuh/ui` multi-step dialog primitive
**Confidence:** HIGH (every load-bearing claim was verified by reading installed source, running the command, or quoting the repo file)

---

## Summary

Phase 3.2 is overwhelmingly a **replication** phase, not a design phase. Two of its three server-side pieces (`floor_plans` + `floor_plan_images` tables, the nested `floorPlans.gallery.*` sub-router, `uploads.presignFloorPlanImage`) have exact, working analogs in `properties`/`property_images`/`properties.gallery`/`uploads.presignPropertyImage` that can be copied statement-for-statement. The staged-gallery frontend pattern is likewise already built and already takes injected callbacks. The genuinely new work is (a) the `WizardDialog` primitive in `packages/ui`, (b) the inherit-vs-override resolution model on `units`, and (c) one schema behaviour the codebase does *not* currently have a precedent for: turning a unique-constraint violation into a **field-level** error.

All four CONTEXT items flagged "verify during planning" resolved cleanly, and three of them resolved *in favour of the simpler branch*:

- **D-07 numeric mode:** `numeric(name, { precision: 4, scale: 2, mode: 'number' })` **is fully supported** in the installed `drizzle-orm@0.45.2`. No service-layer string coercion is needed at either boundary. D-07's fallback branch is dead.
- **D-27 `propertyId` on update:** `updateUnitInputSchema` **does** permit changing `propertyId`, and `updateUnit` already writes it. The unit edit UI explicitly allows reassignment (`unit-form-sheet.tsx` is passed `lockedPropertyId={undefined}` on edit, with a comment saying so). The D-27 conditional therefore fires and must be implemented.
- **D-36 check icon:** `IconCheckmark1` is a real `PlatformIconName`. There is **no** icon suitable for a "current step" dot — that must be Tailwind-drawn.
- **D-29 `dialog.tsx` zero-byte diff:** achievable, and more cheaply than CONTEXT assumes. `DialogContainer` is exported and its class list is `cn()`-merged through `tailwind-merge`, so the wizard can reuse `DialogContainer` directly with `className="flex-row sm:max-w-4xl max-h-[85vh]"` and inherit the rounding, border, shadow, animation *and* the absolute top-right ghost close button for free. No private piece is needed. **Not a blocker.**

The one thing that genuinely threatens this phase is sequencing: **Phase 3.1 is mid-execution right now, not complete.** `createOverlays` / `<AppOverlays>` (plan 03.1-04) do not exist on disk yet. See Blockers.

**Primary recommendation:** Plan the server waves (schema/migration → floorPlans module + uploads + units widening + tests) as pure structural copies of the property/gallery code quoted below, plan `WizardDialog` as a `DialogContainer` re-skin rather than a re-implementation, and make every acceptance criterion that touches the server test suite target **a single test file**, never the whole suite — the suite is red at baseline.

### Locked Decisions

Copied verbatim from `.planning/phases/03.2-floor-plans/03.2-CONTEXT.md` `<decisions>`.

#### Scope & sequencing

- **D-01:** Phase 3.2 sequences **after Phase 3.1 (URL query state)**. The floor plan wizard is a brand-new overlay, so it is registered in the properties module's overlay config from birth (`createOverlays` per 03.1 D-07/D-31) and spreads `overlay.dialogProps` onto `WizardDialog`. Building it before 03.1 would mean writing `useState` plumbing and immediately migrating it.
- **D-02:** The overlay param carries the payload only — `new` for creation, a floor plan id for editing (03.1 D-05). **The active wizard step is NOT in the URL.** A half-completed creation form is not meaningfully shareable and its state would be a lie on cold load (03.1 D-16 — URL-ify only what a user could link to or expect back to undo).
- **D-03:** Floor plans are **property-scoped**: `propertyId` is a non-null FK with `onDelete: 'cascade'`. A landlord with three identical buildings re-creates the plan per property in v1. Org-level reuse is deferred, not designed against.
- **D-04:** **Rent is not a floor plan field.** No `baseRent`, no rent defaults, no rent inheritance. Units keep their existing `baseRent` untouched by this phase.

#### Data model — `floor_plans`

- **D-05:** New table `floor_plans`, following the org-scoped tenant table pattern exactly: `id uuid PK default gen_random_uuid()`, `organizationId text NOT NULL` → `organization.id` cascade, `propertyId uuid NOT NULL` → `properties.id` cascade, `name text NOT NULL`, `bedrooms integer NOT NULL`, `bathrooms numeric(4,2) NOT NULL`, `defaultSquareFootage integer` (nullable), `archivedAt timestamptz` (nullable), `createdAt`/`updatedAt timestamptz NOT NULL default now()`, plus the `organization_isolation` `pgPolicy` and `.enableRLS()`.
- **D-06:** **Name, bedrooms and bathrooms are required; default square footage is optional.**
- **D-07:** `bathrooms` is `numeric(4,2)` supporting **quarter increments** (1.25 / 1.5 / 1.75), validated in Zod as `multipleOf(0.25)`, `min(0)`, `max(20)`. Precision 4 (not 3) because scale 2 with precision 3 caps at 9.99. **Verify during planning** that `drizzle-orm@0.45.2` supports `numeric(..., { mode: 'number' })`; if it does not, the column returns a string and the service layer must coerce at both read and write boundaries — either way, the tRPC contract exposes a `number`.
- **D-08:** `bedrooms` is a plain `integer`, `min(0)`, `max(20)`, where **0 renders as "Studio"** in the UI. Not a Postgres enum.
- **D-09:** Plan names are **unique per property** — `unique('floor_plans_property_name_unique').on(organizationId, propertyId, name)` — mirroring the existing `unit_statuses_org_name_unique`. A collision surfaces as a field-level error on the wizard's name input, not a toast.
- **D-10:** **No `sortOrder` column.** Floor plans are listed alphabetically by name.
- **D-11:** Archiving is **soft** (`archivedAt`) and **does not cascade to units**. An archived plan disappears from assignment pickers but assigned units keep pointing at it and keep inheriting its values.

#### Data model — `floor_plan_images`

- **D-12:** New table `floor_plan_images`, a deliberate near-copy of `property_images`: `id`, `organizationId`, `floorPlanId uuid NOT NULL` → `floor_plans.id` cascade, `objectKey text NOT NULL`, `contentType text NOT NULL`, `byteLength integer NOT NULL`, `sortOrder integer NOT NULL default 0`, `createdAt timestamptz NOT NULL`, plus `organization_isolation` RLS. **No `updatedAt`** and **no soft delete**.
- **D-13:** **No denormalized `propertyId` column.**
- **D-14:** The cap is the **existing `MAX_GALLERY_IMAGES = 25`** constant reused verbatim, enforced server-side in **both** the presign procedure and the add procedure.
- **D-15:** `sortOrder` 0 is the **cover image**; reorder takes a full ordered `imageIds` array and renumbers by index.
- **D-16:** S3 object keys are `{organizationId}/properties/{propertyId}/floor-plans/{floorPlanId}/gallery/{uuid}.{ext}`. Only the `objectKey` is persisted.

#### Data model — `units` additions

- **D-17:** Three columns added to `units`: `floorPlanId uuid` → `floor_plans.id` **`ON DELETE SET NULL`**, `bedrooms integer` (nullable), `bathrooms numeric(4,2)` (nullable). `squareFootage integer` already exists and is already nullable.
- **D-18:** **NULL means "inherit from the assigned plan."** `effective = unit.value ?? plan.value ?? null`. `0` is a real value, not an absence.
- **D-19:** **Inheritance resolves at read time, so plan edits propagate live.** Assignment must **never copy** plan values into unit columns.
- **D-20:** The resolver is a **pure client-side function** in `apps/landlord-web/modules/units/lib/`, and `units.list` / `units.get` **stay unjoined**.

#### Migration

- **D-21:** Generated with `drizzle-kit generate`, then **hand-appended** with the two audit triggers. The generated SQL must be **read before applying**.
- **D-22:** `meta/_journal.json` is updated by the generator; the migration lands as `0017_*`. No data backfill is required.

#### API

- **D-23:** New module `apps/server/src/modules/floor-plans/` (`router.ts` / `service.ts` / `schemas.ts`), registered as `floorPlans` in `appRouter`. Schemas exported via a **new `"./schemas/floor-plans"` entry in `apps/server/package.json` exports**.
- **D-24:** The gallery is a **nested sub-router** `floorPlans.gallery.{list,add,reorder,remove}`. Reads use `protectedProcedure`; every mutation uses `permissionProcedure('write')`. Every procedure body runs inside `withOrganization(organizationId, userId, ...)`.
- **D-25:** Presigning lives in the **`uploads` module** as `uploads.presignFloorPlanImage({ floorPlanId, contentType, byteLength, filename? })`.
- **D-26:** `floorPlans.list({ propertyId })` returns each plan plus a **`unitCount`** and a **presigned cover URL**.
- **D-26a:** `floorPlans.list` takes **`includeArchived?: boolean` (default `false`)** and every row carries its `archivedAt`. **The unit form and units table request `includeArchived: true`**; the **assignment picker filters to non-archived**.
- **D-27:** `units.create` and `units.update` accept optional `floorPlanId`, `bedrooms`, `bathrooms`. The service **validates that the referenced plan belongs to the unit's property** and rejects cross-property assignment with `BAD_REQUEST`. **Verify during planning** whether `updateUnitInputSchema` permits changing `propertyId`; if it does, a property change must also clear or re-validate `floorPlanId`.
- **D-28:** **No `PLAN_RESOURCES` change and no `me.get` quota field.**

#### UI — the `WizardDialog` primitive

- **D-29:** New file **`packages/ui/src/wizard-dialog.tsx`**, which **imports and composes** `Dialog`, `DialogPortal`, `DialogOverlay`, `DialogTitle` and `DialogDescription` from `dialog.tsx`. **`dialog.tsx` itself has a zero-byte diff** — an acceptance criterion, not an aspiration.

- **D-33:** Step state is **uncontrolled by default** with optional controlled `step` / `onStepChange`. It **resets to the first step whenever the dialog closes**.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Floor plan CRUD + soft archive | API / Backend (`floorPlans` router + service) | Database (RLS + audit trigger) | Org-scoped write; RLS is the isolation boundary, not the handler |
| Per-property name uniqueness | Database (unique constraint) | API (pre-check → `BAD_REQUEST` for a field-level message) | Constraint is the guarantee; pre-check is the UX. See Pitfall 1 |
| Gallery presign | API (`uploads.presignFloorPlanImage`) | — | Signing key never reaches the browser; cap re-checked here (D-14) |
| Gallery object upload | Browser / Client (`uploadPresignedPut` XHR PUT) | S3/R2 | Bytes never transit the API server |
| Gallery row creation / reorder / delete | API (`floorPlans.gallery.*`) | Database + S3 delete | Row and object lifecycle stay coupled (D-12, no soft delete) |
| Presigned GET URL minting | API (read-time, `presignGet`) | — | CLAUDE.md S3 rule: only `objectKey` persists |
| Image staging + 25-cap UX message | Browser / Client (`acceptImageFiles`) | API (authoritative re-check) | D-41a: server has not seen staged files |
| Wizard step state / navigation gating | Browser / Client (`WizardDialog` context) | — | D-02: explicitly *not* URL state |
| Wizard open/closed + target id | URL (nuqs overlay param) | Browser | D-01/D-02 |
| Inherit-vs-override resolution | Browser / Client (`modules/units/lib/`) | — | D-20; promoted to `apps/server/src/domain/` only when rent math needs it |
| Unit ↔ plan cross-property validation | API (`units` service) | — | D-27; a client check is advisory, the server check is the guarantee |
| Plan `unitCount` + cover URL | API (grouped query + `selectDistinctOn`) | — | D-26; avoids N+1 per card |

**Conclusions the planner can rely on:**

- `numeric('bathrooms', { precision: 4, scale: 2, mode: 'number' }).notNull()` types as `number` on both `$inferSelect` and `$inferInsert`. Reads come back as JS `number`; writes are `String()`-ified for the driver automatically.
- `getSQLType()` emits `numeric(4, 2)`, so `drizzle-kit generate` will produce `"bathrooms" numeric(4, 2) NOT NULL` — matching the existing `"latitude" numeric(9, 7)` shape in `0013_pink_azazel.sql` line 13.
- **D-07's fallback branch is dead code.** There is no read-boundary or write-boundary coercion to write. The tRPC contract exposes `number` natively.
- **Do NOT copy the `properties.latitude/longitude` precedent.** Those are declared *without* a mode (`numeric('latitude', { precision: 9, scale: 7 })`), so they are `string | null`, which is why `properties/service.ts` carries a hand-rolled `toLatLng(value: number | undefined): string | null | undefined` helper (lines 16-19) and `property-form-shared.ts` does `Number(property.latitude)` on the way back. That is the exact string-vs-number bug CONTEXT's `<specifics>` warns about, preserved in the codebase. Floor plans must not reproduce it.

Concrete column shapes:

```ts
// floor_plans
bathrooms: numeric('bathrooms', { precision: 4, scale: 2, mode: 'number' }).notNull(),
// units (nullable override)
bathrooms: numeric('bathrooms', { precision: 4, scale: 2, mode: 'number' }),
```

**Zod side, verified by execution** `[VERIFIED: ran node with zod 4.3.6]`:

```

  1.3    -> false
```

No float-precision workaround is needed: 0.25/0.5/0.75 are exact IEEE-754 binary fractions.

**One residual caveat, MEDIUM confidence:** `numeric(4,2)` with `mode:'number'` round-trips through JS `number`. For bath counts ≤ 20.00 with 2 decimals this is exactly representable and lossless. Do not extend this pattern to money (the repo already stores rent as integer cents — `baseRent: integer('base_rent')` with the comment *"Integer cents (A3) — never float dollars"*).

```ts
export async function updateUnit(tx, organizationId, input): Promise<UnitRow> {
  const { unitId, ...rest } = input
  const existing = await requireUnit(tx, organizationId, unitId)
  if (rest.propertyId !== undefined) await requireProperty(tx, organizationId, rest.propertyId)
  if (rest.statusId !== undefined) await requireUnitStatus(tx, organizationId, rest.statusId)

  // D-27: the unit's effective property after this update — the plan must belong to it.
  const effectivePropertyId = rest.propertyId ?? existing.propertyId
  const propertyChanged =
    rest.propertyId !== undefined && rest.propertyId !== existing.propertyId

  const patch: Partial<typeof units.$inferInsert> = { updatedAt: new Date() }
  if (rest.propertyId !== undefined) patch.propertyId = rest.propertyId
  ...
  if (rest.floorPlanId !== undefined) {
    if (rest.floorPlanId === null) {
      patch.floorPlanId = null
    } else {
      // BAD_REQUEST, not NOT_FOUND: the plan may well exist, just not here (D-27).
      await requireFloorPlanInProperty(tx, organizationId, rest.floorPlanId, effectivePropertyId)
      patch.floorPlanId = rest.floorPlanId
    }
  } else if (propertyChanged && existing.floorPlanId) {
    // The caller moved the unit and said nothing about its plan. Silently keeping
    // it would leave the unit inheriting from a plan of a property it no longer
    // belongs to — the exact hole D-27 exists to close.
    patch.floorPlanId = null
  }
  ...
}
```

**Additional PowerShell 5.1 rules carried forward from 03.1's `<shell_contract>` and re-confirmed here:**

- Sequence with `;`. There is **no `&&`**.
- `rg -E` is `--encoding`, **not** extended regex. `rg -qE` exits `2` with `unknown encoding`, which satisfies any "returns non-zero" criterion and becomes a silent pass. Regex is rg's default; drop the `E`.
- Use `-F` whenever the pattern is literal source text — `(`, `)`, `[`, `]`, `{`, `}`, `$`, `.` are regex metacharacters and unescaped they match the wrong thing rather than erroring.
- Alternation is `a|b`, never `a\|b` (rg reads `\|` as a literal pipe).
- Inner double quotes must be written `\"`; PowerShell 5.1 strips them before the native exe sees them. A pattern that *begins* with `\"` and contains a space gets split into two argv entries — drop the quotes and match the inner text instead.
- **No glob in a path argument.** PowerShell does not expand globs for native commands, so `rg -n 'X' apps/*/app/layout.tsx` hands rg a literal `*` and exits `2` (`os error 123`). Name the files, or use rg's own `--glob` flag (verified working above).
- **New finding, worth adding to the contract:** `2>&1 |` around a pnpm/turbo invocation makes PowerShell wrap turbo's stderr banner in a `NativeCommandError` record, which prints an alarming stack trace even on a fully successful run `[VERIFIED: observed on `pnpm turbo run typecheck 2>&1 | Select-Object -Last 25`, which exited 0 but printed a NativeCommandError]`. Do not pipe turbo output through `2>&1`; run it bare and read the tail from the terminal file.
- **Run every command before recording its result, especially the ones expected to return non-zero.** A malformed command, an unknown flag, and a genuine pass are indistinguishable by exit code alone. (STATE.md documents three verification passes lost to exactly this.)

### Pattern 1: The three-file server module

Every server module in this repo is `router.ts` (procedures + `withOrganization` + permission gate) / `service.ts` (Drizzle, accepts `OrganizationTx`, never touches `ctx`) / `schemas.ts` (Zod, the API contract). `floorPlans` follows it. Two counter-examples exist (`unit-statuses` and `uploads` have no `service.ts` and inline their queries in the router) — **do not follow those**; `properties` is the pattern D-23 names.

```ts
// router.ts — the shape
export const floorPlansRouter = router({
  list: protectedProcedure.input(listFloorPlansInputSchema).query(async ({ ctx, input }) => {
    const { organizationId, userId } = ctx
    return withOrganization(organizationId, userId, async (tx) => ({
      floorPlans: await listFloorPlans(tx, organizationId, input),
    }))
  }),
  create: permissionProcedure('write').input(createFloorPlanInputSchema).mutation(async ({ ctx, input }) => {
    const { organizationId, userId } = ctx
    const floorPlan = await withOrganization(organizationId, userId, (tx) =>
      createFloorPlan(tx, organizationId, input))
    return { floorPlan }
  }),
  ...
  gallery: floorPlanGalleryRouter,
})
```

`withOrganization` signature (`apps/server/src/db/organization.ts` `[VERIFIED]`) — note **three** arguments; CLAUDE.md's shorthand `withOrganization(organizationId, fn)` omits the actor:

```ts
export async function withOrganization<T>(
  organizationId: string,
  actorId: string = 'system',
  fn: (tx: OrganizationTx) => Promise<T>,
): Promise<T> {
  return db.transaction(async (tx) => {
    await tx.execute(sql`SELECT set_config('app.current_organization_id', ${organizationId}, TRUE)`)
    await tx.execute(sql`SELECT set_config('app.current_user_id', ${actorId}, TRUE)`)
    return fn(tx)
  })
}
```
`app.current_user_id` is what the audit trigger records as the actor — omitting `userId` writes `'system'` into `audit_log` for every floor-plan change. Always pass `ctx.userId`.

`permissionProcedure(action)` (`apps/server/src/trpc.ts` lines 45-59) resolves the Better Auth active member, rejects unknown roles, then `isAllowed(orgId, role, action)`. D-24 says **`'write'`** for every floor-plan mutation — note this is deliberately *weaker* than `unitStatuses`, which uses `'admin'` because it is an org-wide catalog. Floor plans are property-scoped content, so `'write'` is right.

### Pattern 2: Read-time inheritance resolution (D-18/D-19/D-20)

**What:** a pure function mapping a unit + its (possibly archived) plan to effective values.
**When to use:** every surface that displays beds/baths/sq ft for a unit.

```ts
// apps/landlord-web/modules/units/lib/resolve-unit-specs.ts
export type UnitSpecSource = "override" | "inherited" | "none"

export type ResolvedSpec = { value: number | null; source: UnitSpecSource; planName: string | null }

export function resolveUnitSpec(
  unitValue: number | null | undefined,
  planValue: number | null | undefined,
  planName: string | null,
): ResolvedSpec {
  // `??` not `||` — D-18: 0 is a real value (a 0-bedroom studio override), not an absence.
  if (unitValue != null) return { value: unitValue, source: "override", planName }
  if (planValue != null) return { value: planValue, source: "inherited", planName }
  return { value: null, source: "none", planName: null }
}
```

**The `source` discriminant is load-bearing, not decoration.** D-46 needs it to render inherited values muted; D-45 needs it to decide placeholder-vs-value. Returning a bare `number | null` would force both call sites to re-derive it.

The plan lookup map is built from `floorPlans.list({ propertyId, includeArchived: true })` per D-26a. **The units table spans multiple properties**, so it needs plans for every property in view — either call `floorPlans.list` per property id present in the rows, or (better) give `listFloorPlansInputSchema` an optional `propertyIds: z.array(z.uuid())` alongside `propertyId`. Flag as an open question below; D-26 specifies `{ propertyId }` singular.

### Pattern 4: Mutation → invalidate (D-47, CLAUDE.md checklist)

The repo has two helpers from `@villuh/api`: `invalidateOnSuccess(utils, [...])` for a bare `onSuccess`, and `invalidateQueries(utils, [...])` when you also toast/redirect. Existing usage, `unit-form-sheet.tsx` lines 89-94:

Per D-47:

| Mutation | Invalidate |
|----------|-----------|
| `floorPlans.create` / `update` / `archive` | `floorPlans.list`, `floorPlans.get`, `properties.get` |
| `floorPlans.gallery.add` / `reorder` / `remove` | `floorPlans.gallery.list`, `floorPlans.list` (cover URL changes) |

### Anti-Patterns to Avoid

- **Prefilling unit fields on plan assignment.** CONTEXT's `<specifics>` calls this "the single most likely way to build this wrong." It silently converts every unit into an override and turns every future plan edit into a no-op. A unit column is written **only** when the user types in it.
- **`||` instead of `??` in the resolver.** `unit.bedrooms || plan.bedrooms` throws away a legitimate `0`-bedroom studio override.
- **Adding a `variant` prop to `DialogContainer`.** Explicitly rejected by D-29 and would violate the zero-byte-diff criterion.
- **Conditionally rendering wizard step panels.** Reintroduces the exact state-loss bug D-35 exists to prevent — and, separately, unmounting a Radix root mid-transition kills its exit animation (03.1 RESEARCH §7.1).
- **Storing a presigned URL.** CLAUDE.md hard rule; `objectKey` only, `presignGet` at read time (default TTL 300s).
- **Widening the selects to 0–20 to "match" the schema.** D-40 forbids it in so many words.
- **A global JSON body parser or any change near webhook routes.** Out of scope, but CLAUDE.md flags it as a repo-wide landmine.

## Common Pitfalls

### Pitfall 1: The unique constraint gives an INTERNAL_SERVER_ERROR, not a field error

**What goes wrong:** D-09 requires a duplicate plan name to surface as a field-level error on the wizard's name input. The precedent CONTEXT points at (`unit_statuses_org_name_unique`) does **not** do this — `unitStatuses.create` inserts straight into the table with no pre-check and no `catch`. A collision raises Postgres `23505`, tRPC has no mapping for it, and the client gets a 500 with an unusable message.
**Why it happens:** the constraint is the *guarantee*; the friendly message is separate work nobody did for unit statuses.
**How to avoid:** in `createFloorPlan`/`updateFloorPlan`, pre-check inside the same transaction and raise `badRequest`:

```ts
const clash = await tx.select({ id: floorPlans.id }).from(floorPlans)
  .where(and(
    eq(floorPlans.organizationId, organizationId),
    eq(floorPlans.propertyId, propertyId),
    eq(floorPlans.name, input.name),
    ...(excludeId ? [ne(floorPlans.id, excludeId)] : []),
  )).limit(1)
if (clash[0]) badRequest('A floor plan with this name already exists for this property')
```
Keep the DB constraint anyway — the pre-check is racy under concurrent writes and the constraint is what makes it safe. Belt and braces, exactly like the 25-image cap.
**Warning signs:** a test that asserts `rejects.toMatchObject({ code: 'BAD_REQUEST' })` on a duplicate name failing with `INTERNAL_SERVER_ERROR`.

### Pitfall 2: Audit triggers are silently missing

**What goes wrong:** `drizzle-kit generate` emits tables, policies, constraints and FKs — but never `CREATE TRIGGER`. The migration applies cleanly, everything works, and nothing is audited. This is Phase 3's own Pitfall 6, and D-21 restates it.
**How to avoid:** hand-append both triggers to the generated `0017_*.sql`, and verify:
```powershell
rg -cF "audit_log_trigger_fn()" apps/server/migrations/0017_*.sql   # must print 2
```
(That path glob works because it is rg's own argument parsing, not PowerShell expansion — but if in doubt, name the file after generating it.)
**Warning signs:** a fresh floor plan create produces no `audit_log` row.

### Pitfall 3: The generated migration silently omits an RLS statement

**What goes wrong:** if `.enableRLS()` or the `pgPolicy` is missed on one of the two new tables, the migration still applies and the app still works — because the app also filters by `organizationId` explicitly. Cross-org isolation is then enforced by application code alone, and one forgotten `where` clause becomes a data leak.
**How to avoid:** D-21's read-before-apply checklist (item 7). Then assert it at the DB level in `floor-plans.test.ts` by attempting a cross-org read with a second caller and expecting `NOT_FOUND`.
**Warning signs:** `rg -cF "ENABLE ROW LEVEL SECURITY" apps/server/migrations/0017_*.sql` prints anything other than `2`.

### Pitfall 4: `??` vs `||` and the disappearing studio

**What goes wrong:** `0` bedrooms means Studio (D-08) and is a legitimate override. Every `||`, every `if (unit.bedrooms)`, and every `Number(x) || null` in the resolver or the form converts that override back into inheritance.
**How to avoid:** `??` and `!= null` throughout. In the form, the empty-string→undefined conversion must be `value.trim() === "" ? undefined : Number(value)` — the existing `unit-form-sheet.tsx` line 128 already does exactly this for `squareFootage`; copy it, don't improvise.
**Warning signs:** typing `0` into Bedrooms and seeing the plan's value reappear.

### Pitfall 5: Schema import cycle between `units.ts` and `floor-plans.ts`

**What goes wrong:** `units.ts` must `import { floorPlans }` for the FK. If `floor-plans.ts` also imports `units` (e.g. for a count helper), the two modules form a cycle and Drizzle's `() => floorPlans.id` thunk may resolve to `undefined` at table-construction time, producing a cryptic error at import.
**How to avoid:** keep the dependency one-directional — `units.ts → floor-plans.ts → properties.ts`, never back. Aggregate queries that need both tables live in `modules/floor-plans/service.ts`, which imports both schema files. This is the same shape as today's `units.ts → properties.ts`.
**Warning signs:** `Cannot read properties of undefined (reading 'id')` thrown from a `pgTable` call at startup.

### Pitfall 6: Property reassignment leaves a foreign plan attached

**What goes wrong:** `units.update({ unitId, propertyId })` is reachable (item 2) and does not touch `floor_plan_id`. A unit moved from Property A to Property B keeps inheriting from A's plan forever. The FK is `ON DELETE SET NULL`, not `ON UPDATE`, so Postgres will not notice.
**How to avoid:** the `propertyChanged` branch in item 2's `updateUnit`.
**Warning signs:** none in the UI — the unit just shows numbers from a plan that is not in its property's picker. This one is invisible without a test.

### Pitfall 7: Abandoned wizard leaves S3 orphans

**What goes wrong:** the natural implementation presigns and uploads as each file is picked, then creates the plan on Confirm. Abandoning the wizard leaves objects in the bucket with no row, and nothing ever deletes them (the delete path is row-driven).
**How to avoid:** D-41's staging — nothing is presigned until Confirm. This is also why `presignFloorPlanImage` needs a `floorPlanId` that does not exist yet, which is the actual forcing function.
**Warning signs:** the verification scenario "abandon the wizard mid-gallery and confirm no S3 object was created" fails.

### Pitfall 8: `packages/ui` cannot import app code, and its vitest project is node-only

**What goes wrong:** `wizard-dialog.tsx` lives in `packages/ui`, which has `next` only as a peer/dev dependency and has no jsdom. Any attempt to test the wizard's rendering, or to import anything from `apps/landlord-web`, fails.
**How to avoid:** keep `wizard-dialog.tsx` dependency-free beyond `react` + `radix-ui` + local `dialog.tsx`/`icon.tsx`/`cn`. Per D-49, wizard behaviour is manually verified. If a pure step-resolution helper is extracted (e.g. `nextReachableStep(steps, current, mode, visited)`), it **can** be unit-tested — but the vitest config's `include` is `["src/query-state/**/*.test.ts"]` `[VERIFIED]`, so a `wizard-dialog.test.ts` at `src/` root **would not run**. Either widen `include` (a `packages/ui/vitest.config.ts` edit, which is allowed — D-29 protects only `dialog.tsx`) or put the helper under `src/query-state/`, which would be wrong. Widening `include` to `["src/**/*.test.ts"]` is the clean move.
**Warning signs:** a test file that "passes" because it never ran. Always check the reported test-file count.

### Pitfall 9: Gating acceptance on the whole server test suite

See Blocker 2. `pnpm turbo run test --filter=@villuh/server` is red today.

### Pitfall 10: `tailwind-merge` does not know your custom classes

**What goes wrong:** Route A relies on twMerge resolving `sm:max-w-md` vs `sm:max-w-4xl` and `flex-col` vs `flex-row`. Both are standard Tailwind groups, so this works. But `rounded-4xl` is a **v4 extended scale** — if a future className tries to override it with an arbitrary value, verify visually rather than assuming.
**How to avoid:** the wizard's className should only override `max-w-*`, `max-h-*` and `flex-direction`. Everything else is inherited on purpose.
**Warning signs:** the wizard renders at `sm:max-w-md` (both classes present, wrong one winning) — inspect the element's computed class list.

### Pure display helper — `modules/properties/lib/floor-plan-display.ts` (D-39)

```ts
export type FloorPlanSpecs = {
  bedrooms: number
  bathrooms: number
  defaultSquareFootage?: number | null
}

/** "Studio · 1.75 ba · 1,100 sq ft" / "2 bd · 1 ba" */
export function formatFloorPlanSpecs(plan: FloorPlanSpecs): string {
  const parts: string[] = []
  // D-08: 0 bedrooms is a studio, not "0 bd".
  parts.push(plan.bedrooms === 0 ? "Studio" : `${plan.bedrooms} bd`)
  // Trim the trailing zeros numeric(4,2) would otherwise imply: 1.00 -> "1", 1.50 -> "1.5".
  parts.push(`${formatBathrooms(plan.bathrooms)} ba`)
  // D-39: omit absent square footage entirely rather than rendering a dash.
  if (plan.defaultSquareFootage != null) {
    parts.push(`${plan.defaultSquareFootage.toLocaleString()} sq ft`)
  }
  return parts.join(" · ")
}

export function formatBathrooms(value: number): string {
  return Number.isInteger(value) ? String(value) : String(value)   // 1.75 -> "1.75", 1.5 -> "1.5"
}
```

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-org floor plan read/write via a guessed uuid | Elevation of Privilege | RLS policy on `floor_plans` + explicit `eq(organizationId)` in every service query. Test asserts `NOT_FOUND` |
| **Cross-property plan assignment** (in-org, so RLS does not stop it) | Tampering | **Application-level check only** — `requireFloorPlanInProperty` in `units` service, `BAD_REQUEST` (D-27). This is the one authorization decision RLS cannot make, which is exactly why D-48 mandates a test for it |
| Silent inheritance from a foreign property after a unit's `propertyId` changes | Tampering | The `propertyChanged` branch clearing `floorPlanId` (Pitfall 6) |
| Path traversal via `filename` into the S3 key | Tampering | `filename` is accepted and discarded; the key is `randomUUID()` + an extension looked up from a fixed `EXTENSION_BY_CONTENT_TYPE` map. Preserve both properties |
| Bucket flooding via unbounded uploads | Denial of Service | 25-image cap at presign **and** at add (D-14); 10 MB per file; both server-side |
| Content-type spoofing (a `.exe` sent as `image/png`) | Tampering | MIME allowlist gates presign only — the bucket is not a content sniffer. **Accepted risk, unchanged from Phase 3**: objects are served only through short-lived presigned GETs rendered into `<img>`, never executed or served from an app origin |
| Presigned URL leakage (Referer, shared screenshot) | Information Disclosure | 300s TTL, minted per read, never persisted. Accepted |
| Orphaned S3 objects from an abandoned wizard | (resource, not a breach) | D-41 staging — nothing is presigned until Confirm |
| Missing audit trail on a floor plan change | Repudiation | Two hand-written `AFTER INSERT OR UPDATE OR DELETE` triggers (D-21); `withOrganization` sets `app.current_user_id` so the actor is recorded, not `'system'` |
| Stored XSS via a plan name | Tampering | React escapes text nodes; no `dangerouslySetInnerHTML` in any file this phase touches. Plan `name` is plain text (unlike property `notes`, which goes through `sanitizeNotesHtml`) — do **not** add rich text here |

## Open Questions

1. **Does the units table need a multi-property `floorPlans.list`?**
   - What we know: D-26 specifies `floorPlans.list({ propertyId })`. D-26a says the units table builds its resolution map from this list with `includeArchived: true`. The global `/units` table spans every property in the org.
   - What's unclear: how the units table gets plans for N properties from a single-property endpoint.
   - Recommendation: add `propertyIds: z.array(z.uuid()).optional()` to `listFloorPlansInputSchema` as a sibling of `propertyId`, mirroring the `filterIdListSchema` pattern `units.list` already uses. This is inside D-26's spirit (one grouped query, no N+1) and does not contradict any locked decision. Flag it to the user rather than silently widening the contract.

2. **`StagedGalleryField` copy in the wizard.**
   - What we know: its empty state reads *"Drop in property photos — they upload when you save."* D-43 says `persistStagedGallery` is the only pre-existing code touched.
   - What's unclear: whether "property photos" appearing inside a floor-plan wizard is acceptable.
   - Recommendation: accept it for this phase and note it, OR add two optional copy props (`emptyTitle`, `emptyDescription`) with the current strings as defaults — a strictly-additive change that keeps the property form byte-identical in behaviour. Ask the user; do not decide silently.

3. **Should `packages/ui/vitest.config.ts`'s `include` be widened?**
   - What we know: `include: ["src/query-state/**/*.test.ts"]`. D-49 permits unit-testing pure helpers in that project.
   - What's unclear: whether any wizard helper is pure enough to be worth extracting.
   - Recommendation: decide during planning. If yes, widen to `["src/**/*.test.ts"]` and say so explicitly in a plan's `files_modified`. If no, record "no `packages/ui` test change" so the absence is a decision rather than an oversight.

4. **Where does the floor plan overlay key live?**
   - What we know: D-37 puts floor plans inside `modules/properties/`. 03.1-07 creates `properties.overlays.ts` with `{ archive, tags, photo }`.
   - What's unclear: the key name. `plan` collides conceptually with billing plans; `floorPlan` is clearer.
   - Recommendation: `floorPlan: entity(FloorPlanWizard)` → URL key `property.floorPlan`, value `"new"` or a plan uuid (D-02). The 03.1 registry enforces key uniqueness at module scope, so a collision would throw at import — safe either way.

5. **`floorPlans.get` — is it needed?**
   - What we know: D-47 lists `floorPlans.get` in the invalidation set, implying it exists. D-42's edit mode needs the plan's values, and `floorPlans.list` already returns full rows.
   - Recommendation: implement `floorPlans.get({ floorPlanId })` anyway. The wizard opened from a cold deep link (`?property.floorPlan=<id>`) has no list in cache and needs a by-id read for `<OverlayBody>`'s NOT_FOUND branch to work at all.
